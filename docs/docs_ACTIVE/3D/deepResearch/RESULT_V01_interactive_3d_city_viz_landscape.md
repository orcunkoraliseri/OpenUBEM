## Table 1 — The method families for interactive 3D UBEM/city visualization

|---|---|---|---|---|

## Part C — Synthesis (the family recommendation)

### 1. Landscape Location of OpenUBEM's Proposed Viewer
OpenUBEM's proposed viewer architecture—where a Python pipeline compiles 3D geometries and attributes into a web-renderable format that is then opened directly in a local browser—belongs to the **Raw WebGL library (three.js)** family. The UBEM visualization literature widely recognizes this family as highly sound and standard for neighbourhood-scale output visualization. Peer-reviewed research, such as the development of UMI (*Dogan & Reinhart, 2013*), relies on WebGL-based visualization dashboards to show detailed per-building and per-surface solar/thermal metrics. By bypassing heavy server-side GIS engines, this family ensures that model geometry can be rendered exactly as simulated, while supporting dynamic attribute recolouring directly in the client.

### 2. Recommended Primary Family + Fallback
*   **Primary Family**: **Raw WebGL library (three.js)**. This choice allows OpenUBEM to render both the neighbourhood LOD (surfaces-only masses) and the detailed building LOD (with sub-surface windows) while enabling per-surface output mapping (like the Torino solar heat-map) within a single, self-contained HTML page.
*   **Secondary/Fallback Family**: **Map-GL extrusion (MapLibre)**. This serves as a lightweight, low-overhead fallback for fast neighbourhood-scale visualization. It allows users to quickly inspect building masses and color them by EUI or archetype across thousands of buildings without generating complex 3D meshes, at the cost of losing sub-surface details.
*   **Tertiary/Specialized Fallback**: **CityJSON (ninja)**. When users require semantic GIS exports, OpenUBEM can export CityJSON files to be loaded into the ninja viewer.

### 3. Downstream Prompts Roadmap
Downstream prompts should detail the following aspects of the chosen families:
*   `V02` (Peer tools): Detail how specific tools utilize these families (e.g., UMI uses three.js, CEA uses deck.gl, Torino uses Cesium).
*   `V03` (Formats): Focus on **glTF/glb** (for the raw WebGL/three.js stack), **GeoJSON** (for Map-GL extrusion), and **CityJSON** (for the semantic viewer stack).
*   `V04` (LOD): Focus on mapping IDF surfaces to glTF mesh groups to represent different LODs.
*   `V05` (Attributes): Detail how attributes bind to glTF geometries (via property tables or custom user data fields) and GeoJSON properties.
*   `V06` (Render Stack): Formally decide between three.js and deck.gl/MapLibre/Cesium for the implementation, confirming three.js as primary.
*   `V07`–`V15`: Align with the raw WebGL/three.js primary delivery path.

### 4. Table-Stakes Gap in OpenUBEM's Current Visualizer
OpenUBEM's current static approach lacks **dynamic, attribute-driven interaction and temporal playback**. For a city-scale energy model, being able to dynamically orbit a scene, select a building to inspect its parameters, and animate hourly energy/solar demand profiles over an 8760-hour timeseries using a time-slider is considered the basic standard (as seen in the Torino heat-map and UBEM.io). Static matplotlib PNGs and non-interactive COLLADA/OBJ files force the user out of the exploration loop, preventing them from identifying spatial-temporal anomalies in simulation results.

## Confidence and Caveats

*   **Coordinate Projection Stability (High Risk)**: The static renderers in OpenUBEM work in **recentred local metres**, which ignores global geospatial Coordinate Reference Systems (CRS). When integrating with a basemap or projecting back to latitude/longitude, small arithmetic mismatches can cause buildings to float, sink, or warp.
*   **Memory Exhaustion on Low-End Client Machines**: Because the Raw WebGL library is client-side, loading unsimplified 3D meshes for hundreds of buildings with complex windows can exhaust browser memory on standard consumer hardware if the file is not compressed (e.g. using Draco compression).
*   **Lack of Standard Python-to-3DTiles Pipelines**: Generating spatial tilesets natively in Python is still relatively immature compared to standard OBJ/glTF writers. Relying on 3D Tiles introduces a dependency on external compilation binaries.
