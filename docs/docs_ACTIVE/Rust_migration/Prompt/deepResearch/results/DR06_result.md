## Executive Summary

1. **GO for `openubem-results` (Phase 1, R1) using `rusqlite` (`0.43.0`, `bundled`) + `csv` (`1.4.0`) + `arrow`/`parquet` (`60.x`) + `rayon`.** OpenUBEM currently opens each `eplusout.sql` up to 3–4 separate times sequentially per building (`parse_building_sql`, `_parse_meters_sql`, `resolve_simulated_floor_area`, `check_building_integrity` in [`parser.py`](../../../../../../openubem/results/parser.py)) inside a `success_rows.iterrows()` loop ([`results/__init__.py`](../../../../../../openubem/results/__init__.py#L150)), and parses each `eplusout.csv` **twice** via `csv.DictReader` ([`european_campaign.py`](../../../../../../openubem/results/european_campaign.py#L48-L88)). Consolidating into a single open-read-close pass per building across a `rayon` thread pool eliminates redundant opens, pandas row/object allocation, and double CSV passes.
2. **Never enable `PRAGMA mmap_size > 0` or `WAL` recovery unconditionally on HPC network filesystems (Lustre / GPFS).** On Lustre/GPFS/NFS, file truncation or out-of-sync metadata causes `SIGBUS` crashes that SQLite cannot catch as `SQLITE_IOERR` ([sqlite.org](https://www.sqlite.org/mmap.html)), and unrecovered `-wal`/`-shm` sidecars cause `SQLITE_OPEN_READ_ONLY` to fail or `immutable=1` to read stale uncheckpointed data ([sqlite.org](https://www.sqlite.org/uri.html#uriimmutable)). Gate `PRAGMA mmap_size` to local SSD/NVMe (APFS/NTFS) only, keep `mmap_size = 0` on network mounts, and prefer local node scratch (`$SLURM_TMPDIR`) on HPC.
3. **Expect significant Windows Defender / NTFS and macOS `ulimit -n` effects at 10k–40k files.** On Windows NTFS, synchronous real-time scanning (`MsMpEng.exe`) intercepts every `CreateFile`/`Open`/`Close` across 40k small files unless the campaign directory is excluded or on a Windows 11 Dev Drive. On macOS APFS, default soft `ulimit -n` (often `1024`) will trigger `SQLITE_CANTOPEN` / `Too many open files` if connections are pooled across many `rayon` threads; strict **open-read-close** (one short-lived `Connection` per building task, bounded by `rayon` worker count) avoids descriptor exhaustion.
4. **Return `pyarrow.Table` zero-copy via `pyo3-arrow` (`0.21.0`) for `aggregator.py::join_results`, and stream directly via `parquet::arrow::ArrowWriter` for large/standalone Parquet exports (`05_results.parquet`).** Because `aggregator.py` joins `metrics_df` onto `enriched_gdf` and writes `05_results.gpkg` / `05_results.geojson` / `05_results.csv` ([`aggregator.py`](../../../../../../openubem/results/aggregator.py#L250-L305)), returning a `pyarrow.Table` via the Arrow PyCapsule Interface avoids serializing an intermediate Parquet file during in-memory aggregation while supporting direct streaming `ArrowWriter` output for large sweeps (`>100k` buildings or standalone `05_results.parquet` archiving).
5. **Reject the `geos` Rust crate (`11.3.1` / `geos-src`) due to the `LGPL-2.1-or-later` wheel-bundling trap.** Even though `geos`, `geos-sys`, and `geos-src` declare `MIT` in `Cargo.toml` metadata (bypassing naive `cargo-deny` crate-manifest scans), the underlying C++ `libgeos` library is `LGPL-2.1-or-later` ([libgeos.org](https://libgeos.org/)). Static linking (`geos-src`) triggers LGPL-2.1 §6 / LGPL-3.0 §4(d) relinking/object-file distribution duties, and bundling `libgeos` `.so`/`.dylib`/`.dll` via `auditwheel`/`delocate`/`delvewheel` triggers `auditwheel`'s explicit copyright/bundling obligation and violates OpenUBEM's `Apache-2.0 OR MIT` / NG5 guardrail.
6. **Pure-Rust `geo` (`0.33.1`) now has `BooleanOps` (backed by `i_overlay`), `Buffer`, `Validation`, and `MakeValid` (`repair_polygon`), but does NOT match `shapely` 2.0 / GEOS semantics 1-for-1.** `shapely` 2.0 already runs vectorized C/C++ GEOS ufuncs and `STRtree` with the GIL released ([shapely docs](https://shapely.readthedocs.io/)). Porting the 5,669 LOC of `european_residential.py` and `european_nocore.py` is **NO-GO** unless Phase 0 profiling proves a specific hot loop dominates wall time.
7. **`i_overlay` (`9.2.0`) uses fixed-point integer scaling (`i_float`) under the hood, introducing grid-quantization differences vs GEOS.** For `f64` inputs, `i_overlay` computes a power-of-two scale factor, snaps coordinates to an integer grid, executes exact integer sweep-line booleans, and unscales back to `f64` ([iShape-Rust/iOverlay](https://github.com/iShape-Rust/iOverlay)). This makes it robust and fast, but areas/vertices near edge cases can differ slightly from GEOS `OverlayNG`.
8. **Targeted `R6` win is viable ONLY if Phase 0 T02 profiling proves `_resolve_overlaps` or `discover_context` is a bottleneck.** Replacing just the Python `iterrows()` / `sindex.query` loops in [`footprint_schema.py`](../../../../../../openubem/acquisition/footprint_schema.py#L25-L44) (`_resolve_overlaps`) and [`context.py`](../../../../../../openubem/geometry/context.py#L32-L69) (`discover_context`) with `rstar` (`0.14.0`) + `geo`/`i_overlay` avoids touching `european_*.py`, **provided** `shapely` 2.0 vectorized ufuncs (`shapely.intersection`, `shapely.union`, `shapely.minimum_rotated_rectangle`) aren't already cheaper to adopt in 20 lines of Python first.

## Q1 — Parallel Rust SQLite + CSV Harvester (`openubem-results`)

### 1.1 Current OpenUBEM Bottleneck on Disk

Inspection of OpenUBEM's existing results pipeline shows why harvesting 8,139–40,800 building directories is slow today:

1. **Sequential per-building loop:** [`openubem/results/__init__.py#L150`](../../../../../../openubem/results/__init__.py#L150) iterates `for _, sim_row in success_rows.iterrows():` and calls `parse_building()` one building at a time.
2. **Repeated SQLite open/close per building:** Inside [`openubem/results/parser.py`](../../../../../../openubem/results/parser.py), a single building opens `eplusout.sql` up to **four separate times**:
   - `parse_building_sql` (line 121): `sqlite3.connect(...)` + `pd.read_sql_query(HOURLY_QUERY, conn)` pulling every hourly variable row into Python/pandas DataFrames (then filtering in pandas).
   - `_parse_meters_sql` (line 212): reopens `sql_path` to run `METER_QUERY` and `_read_abups_district_heating_rows` (14 `TabularDataWithStrings` ABUPS District Heating rows).
   - `resolve_simulated_floor_area` (line 572): falls back to `parse_sql_zone_area(sql_path)` if `eplusout.eio` is missing/unusable.
   - `check_building_integrity` (line 865): reopens `sql_path` again for ABUPS cross-check, `Electricity:Facility` meter closure, and `NaturalGas:Facility` checks.
3. **Double-pass Python CSV parsing:** [`openubem/results/european_campaign.py#L37-L99`](../../../../../../openubem/results/european_campaign.py#L37-L99) (`extract_four_end_use_eplus_csv`) opens every `eplusout.csv` **twice** using Python `csv.DictReader`: pass 1 (lines 48–77) constructs a Python `dict` per row across 8,760 rows to sum 4 end-use variables; pass 2 (lines 85–88) reopens the file with `csv.DictReader` solely to count row occurrences per month against `NON_LEAP_MONTH_HOURS = (744, 672, 744, 720, 744, 720, 744, 744, 720, 744, 720, 744)`. Likewise, `parse_building_csv` ([`parser.py#L232-L276`](../../../../../../openubem/results/parser.py#L232-L276)) uses `pd.read_csv()` followed by `raw.iterrows()` and `datetime.strptime()` per row.

### 1.2 Expected Performance of `rusqlite` + `csv`/`memchr` + `rayon` vs Python `sqlite3` + `pandas`

- **Separating Measured vs Projected Speedups:**
  - **Measured published baselines:**
    - *SQLite → DataFrame:* In the VLDB ConnectorX paper ([`sfu-db/connector-x`](https://github.com/sfu-db/connector-x)), Rust-native SQLite extraction into columnar DataFrame memory outperformed `pandas.read_sql` by **2.3× to 5.2×** on single-database TPC-H / DDoS workloads by eliminating Python row-by-row DBAPI marshalling and intermediate chunk copies.
    - *CSV parsing (`rust-csv` vs `csv.DictReader`):* BurntSushi's `csv` crate (`1.4.0`) + `xsv` benchmarks on a 1M-row CSV (`worldcitiespop_mil.csv`) measured **~413 MB/s** (`count`) and **~325–350 MB/s** (`select`/`search`), and `rust-csv` read/write micro-benchmarks span **~100–440+ MB/s** single-threaded ([BurntSushi/xsv](https://github.com/BurntSushi/xsv), [BurntSushi/rust-csv](https://github.com/BurntSushi/rust-csv)). By contrast, Python `csv.DictReader` allocates a fresh `dict` and string objects per row, typically yielding **~10–30 MB/s** (hardware/row-width dependent; exact OpenUBEM `eplusout.csv` baseline `UNVERIFIED`).
  - **Projected OpenUBEM gains (`PROJECTED / UNVERIFIED` until Phase 1 T06 benchmarks on actual 8k–40k corpora):**
    - Replacing 3–4 sequential `sqlite3` opens + `pd.read_sql_query` + pandas `groupby`/`merge` per building with **1 open-read-close `rusqlite` connection per building** running SQL-side aggregation or typed `stmt.query_map` across `rayon` threads (8–12 cores on M2 Pro, up to 32 cores on Speed HPC) avoids Python/pandas frame overhead entirely and parallelizes independent files linearly up to storage IOPS / MDS limits.
    - Replacing double-pass `csv.DictReader` in `european_campaign.py` with a **single-pass** `csv::Reader` (`ByteRecord` reuse, counting month rows in `[u32; 12]` during the same pass that sums the 4 end-use columns) eliminates 50% of file opens and Python `dict` allocations, scaling across `rayon` cores.
    - *Note on `sqlx` vs `rusqlite`:* `sqlx` (`0.9.1`) still links `libsqlite3-sys` (C SQLite) under the hood while imposing Tokio async runtime and background worker-channel overhead. For batch-harvesting thousands of local read-only `.sql` files, synchronous `rusqlite` (`0.43.0`, `bundled`) + `rayon` is strictly faster and simpler.

### 1.3 Exact Filesystem, Concurrency, and Memory Caveats (APFS, NTFS, Lustre/GPFS)

| Dimension | macOS APFS (Local NVMe, M2 Pro) | Windows NTFS (Local NVMe + Defender) | HPC Parallel Scratch (Lustre / GPFS) |
|---|---|---|---|
| **Connection Pooling vs Open-Read-Close** | **Use strict open-read-close** (1 `Connection` opened, all 3–4 queries executed, and dropped per building task). Never hold 10k–40k connections in a pool: macOS soft `ulimit -n` defaults to as low as **1,024** (enforced via `OPEN_MAX` unless raised via `ulimit -n` / `setrlimit`), so pooled handles cause `SQLITE_CANTOPEN` / `Too many open files` ([stackoverflow](https://stackoverflow.com/), [sqlite.org](https://www.sqlite.org/)). | **Use strict open-read-close**, and **cap `rayon` concurrency / exclude campaign folder in Windows Defender.** Real-time AV (`MsMpEng.exe`) synchronously intercepts `Create`/`Open`/`Close`/`Read` on every small file, pinning a CPU core and throttling 40k-file harvests unless excluded (`Add-MpPreference -ExclusionPath`) or placed on a Windows 11 ReFS **Dev Drive** (async AV scanning). | **Minimize `open()`/`stat()` calls per file** (1 open for `eplusout.sql`, 1 for `eplusout.eio`). Lustre MDS (Metadata Server) / GPFS token manager suffer severe RPC storms when thousands of files are opened concurrently across nodes ([CMU PSC / HPC Lustre docs](https://www.psc.edu/)). Do not exceed moderate thread counts (e.g., 8–16 threads on shared Lustre), or stage/tarball to node-local NVMe (`$SLURM_TMPDIR`) first. |
| **`PRAGMA mmap_size` & `SIGBUS` Pitfalls** | **Safe on internal APFS SSDs**, but note `mmap_size` is **per connection**. If 12 `rayon` threads simultaneously map 256 MB each, virtual address reservation hits ~3 GB (fine for 64-bit, but keep `mmap_size` modest, e.g., `16_777_216`–`67_108_864` bytes since `eplusout.sql` is 0.5–15 MB). Do not `mmap` external/unmountable volumes. | **Safe on local NTFS NVMe** for 0.5–15 MB files; note `mmap` reduces `ReadFile` syscall frequency, though initial `CreateFile` Defender interception still dominates if unexcluded. | **HAZARD — Set `PRAGMA mmap_size = 0;` on Lustre/GPFS/NFS.** If any external process truncates or alters file size while distributed metadata caches lag, accessing mapped pages past EOF triggers a hardware **`SIGBUS`** crash that SQLite cannot catch as `SQLITE_IOERR` ([sqlite.org/mmap.html](https://www.sqlite.org/mmap.html)). |
| **SQLite `WAL` / Read-Only URI Locks on Partial Crash Files** | If an EnergyPlus or post-process crash left stale `-wal` / `-shm` sidecar files on a DB in `WAL` mode, opening with `SQLITE_OPEN_READ_ONLY` (`?mode=ro`) **still tries to open/map `-shm` and requires directory write permission**; read-only connections **cannot run WAL crash recovery** and may fail with `SQLITE_READONLY` / `SQLITE_CANTOPEN` / `SQLITE_BUSY` ([sqlite.org/wal.html](https://www.sqlite.org/wal.html)). | Same SQLite WAL rules: stale `-wal`/`-shm` or crashed locks cause read-only open failures; additionally, Windows mandatory file locks from orphaned processes prevent opening until handles close. | **Critical HPC failure mode:** WAL `-shm` relies on shared-memory `mmap` + POSIX `fcntl` byte-range locks, which fail (`SQLITE_IOERR_SHMOPEN` / locking protocol error) or corrupt data on Lustre/GPFS/NFS ([sqlite.org/wal.html](https://www.sqlite.org/wal.html)). |
| **`?immutable=1` URI Flag Trade-Off** | Useful only if guaranteed static & checkpointed; **DO NOT use blindly on partial/crashed runs**, because `immutable=1` skips `-wal`/`-shm` entirely and silently ignores uncheckpointed WAL frames, returning stale or incomplete data ([sqlite.org/uri.html#uriimmutable](https://www.sqlite.org/uri.html#uriimmutable)). | Same: silently ignores uncheckpointed `-wal` frames on crashed runs. | Only safe on Lustre/GPFS if EnergyPlus wrote in default `DELETE` journal mode (standard for E+ `eplusout.sql`) and no `-wal`/`-journal` exists. Detect non-empty `-wal` / `-journal` files before opening and flag those buildings as `failed_incomplete` rather than silently reading corrupt state! |

**Actionable design for `openubem-results`:**
1. Open each `eplusout.sql` **once** with `OpenFlags::SQLITE_OPEN_READ_ONLY | OpenFlags::SQLITE_OPEN_URI` (`mode=ro`, **without** `immutable=1` by default, or only if no sibling `-wal`/`-journal` exists; reject/flag any building with a non-zero orphan `-journal` or uncheckpointed `-wal` unless explicitly checkpointed).
2. Auto-detect filesystem type or expose an explicit `mmap_bytes` config (default `0` on Linux HPC / network mounts, `33_554_432` [32 MB] on local APFS/NTFS).
3. Configure `conn.busy_timeout(Duration::from_millis(2000))` defensively.
4. Execute `HOURLY_QUERY` (or SQL-aggregated zone lighting/equipment + IOD site/operative/occupancy filters), `METER_QUERY`, `TabularDataWithStrings` (all 14 ABUPS District Heating rows), `Zones` (floor area + multipliers), and `check_building_integrity` queries **on that single open `Connection`**, plus read sibling `eplusout.eio` via `memchr` early-exit scan (`! <Zone Information>`).

## Q2 — Zero-Copy Arrow / Parquet Output (`pyo3-arrow` vs `ArrowWriter`)

OpenUBEM's Step 5 pipeline currently splits responsibilities across two layers:
- `openubem/results/__init__.py` constructs `metrics_df` (one row per building: 10 EUIs + district-heating split provenance + GWPs + `iod` + `floor_area_m2` + `floor_area_provenance` + `simulation_status` + `data_quality_flag` + `error_summary`).
- `openubem/results/aggregator.py` (`join_results` + `export_results`, lines 95–305) left-joins `metrics_df` onto `enriched_gdf` (`GeoDataFrame`) and writes `05_results.gpkg`, `05_results.schema.json`, `05_results.geojson`, `05_results.csv`, and `05_neighbourhood_summary.json` (plus `05_results.parquet` targeted in Phase 1).

Comparing the two Rust output paths:

| Dimension | Path A: Return `pyarrow.Table` via `pyo3-arrow` (`0.21.0`) | Path B: Stream directly to `05_results.parquet` via `parquet::arrow::ArrowWriter` |
|---|---|---|
| **Memory & Zero-Copy Mechanics** | Uses the **Arrow PyCapsule Interface** (`__arrow_c_array__` / `__arrow_c_stream__`) via `pyo3_arrow::PyTable` (or `PyRecordBatchReader` for streaming) and `.to_pyarrow(py)` ([docs.rs/pyo3-arrow](https://docs.rs/pyo3-arrow)). Zero-copy buffer ownership transfer from Rust `Vec<RecordBatch>` to `pyarrow.Table` (`pyarrow >= 14`/`15`), and convertible to pandas `ArrowDtype` with minimal overhead. | Releases the Python GIL (`py.allow_threads`), builds bounded `RecordBatch` chunks (e.g., 4,096–16,384 buildings per row group), and writes compressed Parquet row groups incrementally via `parquet::arrow::ArrowWriter` (`parquet 60.x`). Peak Rust RAM is $O(\text{row\_group\_size})$, never holding the full dataset in Python. |
| **Throughput & Overhead** | For 10k–40k building summary rows (~35–45 columns), a combined `pyarrow.Table` is tiny (**~3–15 MB** in RAM) — building it in Rust and handing pointers via PyCapsule takes sub-millisecond FFI overhead and eliminates any intermediate disk write+read if `aggregator.py` immediately joins `metrics_df` onto `enriched_gdf` in Python. | For **hourly** time-series dumps (40,000 buildings × 8,760 hours × multiple variables = **>350M+ rows**, tens of GB), holding a single `pyarrow.Table` in RAM will OOM a laptop/node. Streaming `ArrowWriter` handles larger-than-memory outputs safely and achieves native Rust Parquet encoding speeds without Python/PyArrow GIL or serialization overhead. |
| **Downstream Compatibility** | Directly feeds `aggregator.py::join_results(enriched_gdf, metrics_df)` (`metrics_df = table.to_pandas(types_mapper=pd.ArrowDtype)` or Polars `pl.from_arrow(table)`), `05_results.gpkg`, `05_results.geojson`, `05_results.csv`, and `OPENUBEM_RUST_BACKEND="shadow"` diffs. | Produces `05_results.parquet` atomically on disk (write to `.parquet.tmp` then rename); Python still must `pd.read_parquet` / `pyarrow.parquet.read_table` if `aggregator.py` needs the table in memory for `.gpkg`/`.geojson` export. |

**Recommendation for Q2 (Dual-Mode Output):**
- **Default for `openubem-results` building-level summary (`metrics_df`, 10k–40k rows):** Return a `pyarrow.Table` via `pyo3-arrow` (`PyTable::to_pyarrow`), because 40k scalar summary rows occupy only a few MB and feed directly into `aggregator.py::join_results` and `shadow` diffing with zero disk round-trip.
- **Direct `parquet::arrow::ArrowWriter` mode (`harvest_to_parquet(paths, out_path)`):** Provide a streaming Rust entrypoint (taking a `rayon`-produced channel/iterator of `RecordBatch`es into `ArrowWriter::try_new` with ZSTD/Snappy) for (a) writing `05_results.parquet` directly without touching Python memory, and (b) any future full-hourly 8,760-hour export (`>100k`–`350M` rows) where `PyTable` would exhaust RAM.

## Q3 — Geospatial Parity: `shapely` 2.0 (C GEOS) vs Rust `geo` vs `i_overlay` vs `geos` Crate

### 3.1 When Moving Geometry to Rust Wins vs Loses

`shapely` 2.0 merged `pygeos` into a C extension exposing GEOS operations as **NumPy ufuncs** with an `STRtree` spatial index (`tree.query(geoms, predicate=...)`) that executes bulk loops in C/C++ with the GIL released ([shapely docs](https://shapely.readthedocs.io/)). Likewise, `pyogrio` reads/writes `.gpkg` via C++ GDAL/OGR (including `use_arrow=True`).

- **Where Rust LOSES (or barely breaks even):**
  1. **Already-vectorized `shapely` 2.0 array ops:** Calling `shapely.area(arr)`, `shapely.buffer(arr, 0)`, `shapely.is_valid(arr)`, or `shapely.intersection(a_arr, b_arr)` on contiguous geometry arrays already runs in C++ GEOS without Python per-element loops. Porting those to Rust adds FFI boundary marshalling cost (converting Shapely GEOS pointers ↔ WKB/GeoArrow ↔ Rust `geo` structs) that can **erase** any compute gain.
  2. **Complex topological repair pipelines (`european_residential.py` 3,061 LOC + `european_nocore.py` 2,608 LOC):** These modules rely on subtle GEOS behaviors (`buffer(0)` sliver healing, polygon splitting, `minimum_rotated_rectangle`, morphological sweeps). Re-implementing 5,669 LOC in `geo`/`i_overlay` incurs **high semantic drift risk** (divergent sliver/collinear splits) for dubious speedups where GEOS already runs in C++.
- **Where Rust WINS:**
  1. **Python row-wise loops around Shapely (`iterrows()`, `apply(axis=1)`, nested `for` + `gdf.at[idx, "geometry"]`):** Python interpreter frame overhead, pandas indexing (`gdf.at[...]`, `gdf.iloc[...]`), and GIL serialization dominate here — *not* GEOS math. Moving the loop + R-tree (`rstar`) + predicates/overlay (`geo`/`i_overlay`) into a single GIL-released `rayon` call eliminates interpreter and pandas overhead and scales across CPU cores.
  2. **Pure-Rust downstream kernels (`openubem-extrude`, `openubem-shading`):** When geometry is already in Rust (e.g., 3D extrusion in Phase 5a), using `rstar` + `geo` avoids Python/Shapely round-trips altogether.
  3. **Dense polygon overlay batches (`i_overlay`):** Modern scanline clipping (`i_overlay`) with flat arrays and `rayon` often outperforms GEOS's heavier graph construction on pure 2D polygon boolean intersections/unions — *provided* precision differences are acceptable.

### 3.2 Pure-Rust `geo` (`0.28`–`0.33.1`) Parity & Degenerate OSM Robustness

The `geo` crate has matured substantially between `0.28` and `0.33.1` (released 2026-04-20):
- **`BooleanOps` (`geo 0.30+`, Mar 2025 onward):** Replaced the older `geo-booleanop` (Martinez-Rueda) implementation—which suffered from floating-point collapse and panics—with **`i_overlay`** ([georust/geo](https://github.com/georust/geo)). Exposes `.intersection()`, `.union()`, `.difference()`, `.xor()`, and `unary_union`.
- **`Validation` & `MakeValid` (`geo 0.29–0.30+`, Dec 2024 onward):** Native OGC validation (`Validation` trait) and polygon repair (`MakeValid::make_valid() -> Result<MultiPolygon<T>, RepairPolygonError>`) using constrained Delaunay triangulation via **`spade`** (`prepair`-style) ([docs.rs/geo](https://docs.rs/geo)).
- **`Buffer` (`geo::algorithm::buffer` in `geo 0.33.1`):** Provides `.buffer(distance)` and `.buffer_with_style(BufferStyle)` (positive outward / negative inward offsets, `LineCap`, `LineJoin::Miter`).
- **Robustness Gaps vs `shapely` 2.0 / GEOS on Degenerate OSM Footprints:**
  1. **`Buffer` expects valid OGC inputs:** Unlike Shapely's classic `buffer(0)` self-intersection-repair idiom, `geo`'s `Buffer` assumes valid input geometries; passing raw self-intersecting OSM footprints directly to `Buffer` can fail or produce broken contours ([georust/geo](https://github.com/georust/geo)). You must run `make_valid()` first.
  2. **Semantic drift in `make_valid()` vs GEOS `buffer(0)` / `make_valid()`:** `MakeValid` repairs invalid rings via constrained Delaunay triangulation (`spade`), which does not guarantee identical ring selection, hole preservation, or `MultiPolygon` splitting vs GEOS `buffer(0)` (used at [`footprint_schema.py#L82`](../../../../../../openubem/acquisition/footprint_schema.py#L82)) on bowties, spikes, or zero-area slivers — and returns `Err(RepairPolygonError)` on severely degenerate inputs.
  3. **Sharp-corner buffer self-intersections:** Even on valid polygons, large negative/positive offsets with sharp concave angles or tight miters in `geo::Buffer` can yield self-intersecting rings that need secondary validation.

### 3.3 The `geos` Crate Licensing Trap (`LGPL-2.1-or-later` vs `Apache-2.0 OR MIT`)

OpenUBEM is dual-licensed **`Apache-2.0 OR MIT`**, and [`PLAN_rust_migration.md`](../../../PLAN_rust_migration.md) §2 (NG5) & §3 (Guardrail 5) prohibit copyleft dependencies via `cargo-deny` (`deny.toml` allowing only `Apache-2.0`, `MIT`, `BSD-2-Clause`, `BSD-3-Clause`, `ISC`, `Unicode-3.0`, `Zlib`).

Using the Rust `geos` crate (`11.3.1`) creates **three interlocking legal/tooling traps**:

1. **Metadata Blindness in `cargo-deny`:** `geos`, `geos-sys`, and `geos-src` all declare **`MIT`** in `Cargo.toml` ([crates.io/crates/geos](https://crates.io/crates/geos)). Because `cargo-deny` inspects Rust crate manifests, it can pass `geos` as `MIT` while silently pulling C++ **`libgeos` (`LGPL-2.1-or-later`)** ([libgeos.org](https://libgeos.org/)) into the compiled artifact.
2. **Apache-2.0 vs LGPL-2.1 Incompatibility Nuance:** FSF and ASF explicitly classify `Apache-2.0` as **incompatible** with `GPL-2.0` / `LGPL-2.1` *only* due to Apache-2.0 patent-termination/indemnification clauses ([apache.org](https://www.apache.org/licenses/GPL-compatibility.html)). Because `libgeos` is `LGPL-2.1-or-later`, distributors may opt into **`LGPL-3.0`** (which *is* compatible with Apache-2.0), **but** doing so still imposes strict LGPL copyleft obligations on any binary distribution containing `libgeos`.
3. **Static Linking (`geos-src`) vs Wheel Bundling (`auditwheel` / `delocate` / `delvewheel`):**
   - **Static linking (`features = ["static"]` via `geos-src`):** Compiles GEOS `3.14.1` C++ source straight into `openubem._rust` (`.so`/`.pyd`). Under **LGPL-2.1 §6** (and **LGPL-3.0 §4(d)**), static linking is **only** permitted if you distribute relinkable object files (`.o`/`.a` of `openubem._rust`) or complete buildable source + scripts so end users can modify `libgeos` and relink the binary.
   - **Dynamic linking + `maturin` wheel bundling (`auditwheel` on Linux, `delocate` on macOS, `delvewheel` on Windows):** Even if `geos-sys` links dynamically, `auditwheel`/`delocate`/`delvewheel` copy `libgeos_c.so`/`.dylib`/`.dll` directly into the distributable wheel (`.libs/`). `auditwheel`'s own documentation warns: *"Packagers are advised that bundling, like static linking, may implicate copyright concerns."* Distributing bundled `libgeos` binaries inside OpenUBEM's wheel requires shipping the full `LGPL-2.1`/`LGPL-3.0` license text, GEOS copyright notices, and exact corresponding GEOS source code/offer in `.dist-info`/wheel artifacts — violating OpenUBEM's clean `Apache-2.0 OR MIT` wheel distribution policy.

**Verdict on `geos` crate:** **Do NOT use `geos` / `geos-sys` / `geos-src` in OpenUBEM.** Keep GEOS strictly isolated inside Python's pre-existing external `shapely` dependency (`pip`/`uv` installs Shapely's own PyPI wheels), and keep OpenUBEM's Rust crates 100% pure-Rust `Apache-2.0 OR MIT`.

## Q4 — Targeted Win for `_resolve_overlaps` & `discover_context`

### 4.1 What `_resolve_overlaps` and `discover_context` Actually Do

- **`_resolve_overlaps` ([`footprint_schema.py#L25-L44`](../../../../../../openubem/acquisition/footprint_schema.py#L25-L44)):**
  - Loops `for i, idx in enumerate(indices):` in Python, calling `gdf.sindex.query(gdf.at[idx, "geometry"], predicate="intersects")` one polygon at a time.
  - For each pair `(idx, other)` with `pos > i`, executes `a.union(b).area` and `a.intersection(b).area` to check `intersection_area / union_area > 0.95` (note: mathematically $\text{IoU} = \frac{A \cap B}{A \cup B} = \frac{\text{area}(A \cap B)}{\text{area}(A) + \text{area}(B) - \text{area}(A \cap B)}$, meaning `a.union(b)` is mathematically redundant if `a.area` and `b.area` are precomputed—and `footprint_area_m2` is already a column!).
  - Notice that [`seven_step_clean`](../../../../../../openubem/acquisition/footprint_schema.py#L47-L89) also accepts an injectable `overlap_resolver: Callable[[gpd.GeoDataFrame, float], gpd.GeoDataFrame] | None = None` parameter! That makes swapping `_resolve_overlaps` (without touching `european_*.py`) architecturally trivial.
- **`discover_context` ([`context.py#L32-L69`](../../../../../../openubem/geometry/context.py#L32-L69)):**
  - For one target building, computes `influence = target_poly.buffer(sphere_radius_m)` (default `30.0 m`), queries `gdf.sindex.query(influence, predicate="intersects")`, and loops in Python over `candidate_idx` calling `gdf.iloc[idx]` and `ctx_row.geometry.minimum_rotated_rectangle` per neighbor.
  - In district campaigns, `discover_context` is called once per building, meaning **each neighbor's `minimum_rotated_rectangle` is recomputed repeatedly** across overlapping 30 m neighborhoods, alongside `gdf.iloc[idx]` Series allocations!

### 4.2 Can `rstar` + `geo` / `i_overlay` Replace Only Those Loops?

**Yes — cleanly, without touching the 5,669 LOC of `european_residential.py` (3,061 LOC) + `european_nocore.py` (2,608 LOC):**

1. **Before writing Rust, test a 20-line vectorized `shapely` 2.0 optimization in Python:**
   - In `_resolve_overlaps`: bulk-query `pairs = gdf.sindex.query(gdf.geometry, predicate="intersects")` once in C, filter `i < j`, compute vectorized `shapely.area(shapely.intersection(geoms[i], geoms[j]))`, and derive union area via `area[i] + area[j] - inter_area` without calling `.union()` or `gdf.at[...]` in Python.
   - In `discover_context`: precompute `shapely.minimum_rotated_rectangle(gdf.geometry)` once per district (vectorized in C) and bulk-query `gdf.sindex.query(shapely.buffer(target_geoms, 30.0), predicate="intersects")` across all buildings instead of per-building `gdf.iloc[idx]`.
2. **If Phase 0 T02 profiling still shows `_resolve_overlaps` or `discover_context` taking significant wall time (>5–15% of pipeline runtime):**
   - Pass polygon coordinates once across PyO3 via **GeoArrow (`geoarrow` `0.9.0`) or WKB arrays**, build a bulk-loaded `rstar::RTree` (`0.14.0`), run `rayon`-parallel pair evaluation using `geo::BooleanOps` (`i_overlay`) / `geo::Area` / `geo::MinimumRotatedRect`, and return the boolean keep/drop mask + `_overlap_resolved` flags (or packed context OBB coordinate arrays) to Python.

### 4.3 Precision Differences vs GEOS (`i_overlay` Fixed-Point Scaling)

When swapping GEOS (`shapely` 2.0) for `geo` / `i_overlay`, exact numerical differences arise from two sources:
1. **`i_overlay` fixed-point grid quantization (`i_float`):** `i_overlay`'s `f64` API inspects input coordinate bounds, picks a power-of-two scale factor, snaps coordinates onto an integer grid (`i64` / `i32`), performs exact integer sweep-line intersections, and unscales back to `f64` ([iShape-Rust/iOverlay](https://github.com/iShape-Rust/iOverlay)). In UTM metric coordinates (e.g., Easting ~500,000 m, Northing ~4,500,000 m), bounding-box range determines the LSB quantization step (at `i64` with full range over ~10⁷ m, sub-nanometer precision is preserved; if an entire global extent or `i32` path were hit, precision coarsens). Exact ULP delta vs GEOS `OverlayNG` on OpenUBEM's UTM footprints is `UNVERIFIED` until shadow-tested.
2. **Boundary effects near `iou_threshold = 0.95` and `buffer(30.0)`:**
   - For `_resolve_overlaps`, `IoU` is a threshold test (`> 0.95`). Buildings with `IoU` in `[0.949999, 0.950001]` could theoretically flip keep/drop if quantization alters `intersection.area` by $10^{-10}\text{ m}^2$ (rare in practice for nearly identical footprints, since near-identical polygons have $\text{IoU} \approx 0.98\text{--}1.00$ or $< 0.50$, but must be shadow-checked).
   - For `discover_context`, `geo::Buffer` uses segmented circular arcs around corners (default segment count per quadrant may differ from GEOS's default `quad_segs=8`), which can include/exclude a context building whose footprint sits within millimeters of the 30.0 m buffer boundary! Replacing `target_poly.buffer(30.0)` intersection with exact `rstar` distance-to-polygon (`MinimumDistance <= 30.0`) or matching GEOS `quad_segs` resolves this cleanly, though it must pass the `OPENUBEM_RUST_BACKEND="shadow"` corpus gate.
