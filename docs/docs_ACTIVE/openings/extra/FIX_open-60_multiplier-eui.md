## 1. What changed

`lighting_eui_kwh_m2` and `equipment_eui_kwh_m2` are now **zone-multiplier-aware**, matching the
multiplier-aware floor-area denominator `resolve_simulated_floor_area()` already produces. Before
this fix, a zone with `Zone Multiplier x Zone List Multiplier > 1` had its `Zone Lights Electricity
Energy` / `Zone Electric Equipment Electricity Energy` summed once (E+ does not scale these hourly
zone variables by multiplier), while the area it was divided by counted that zone `N` times — so the
numerator and denominator disagreed about how many of that zone existed. This under-counted lighting
and equipment for every `layout_assign` building (`layout_assign` is the only mode that ever writes a
multiplier > 1; `auto` writes multiplier 1 everywhere — see §3).

`openubem/results/parser.py`:
- New function `parse_eio_zone_multipliers(path)` — streams one `eplusout.eio`, returns
  `{ZONE_NAME_UPPER: zone_multiplier x zone_list_multiplier}`. Shares the header marker
  (`_EIO_HEADER_MARKER`), data prefix (`_EIO_DATA_PREFIX`) and field-name constants
  (`_EIO_FIELD_ZONE_MULT`, `_EIO_FIELD_ZONE_LIST_MULT`) with `parse_eio_zone_area()` — same `.eio`
  route, not a second reader. `parse_eio_zone_area()` itself is untouched (it stays a verbatim port
  of the audit script per its own docstring). Never raises; returns `{}` on any failure.
- `_compute_eui()` gained an optional `zone_multipliers: dict[str, float] | None = None` parameter.
  When supplied and non-empty, the lighting/equipment sum is grouped by `key_value` (upper-cased,
  matching the `.upper()` convention already used for zone-name matching elsewhere in this module)
  and each zone's kWh is multiplied by its map entry before summing; a `key_value` absent from the
  map defaults to multiplier `1.0`. When `zone_multipliers` is `None` or `{}` (every pre-OPEN-60 call
  site, including every existing direct test of this function), the sum is bit-identical to before —
  verified by `test_omitted_zone_multipliers_is_bit_identical_to_pre_open60`.
- `parse_building()` now reads `eplusout.eio` (sibling of `sql_path`, the same file
  `resolve_simulated_floor_area()` already opened for the denominator) a second time via
  `parse_eio_zone_multipliers()` and passes the result to `_compute_eui()`. `{}` on any failure
  (file missing, unparsable, no `sql_path`) — `_compute_eui()` then behaves exactly as today.

P10 (missing lighting/equipment variable → `failed_parse`; missing meters → 0.0), the OPEN-46
elevator de-folding, and the pre-OPEN-01 fallback (`floor_area=None` -> `footprint_area x
num_floors`) are all untouched — none of that logic sits inside the changed loop.

## 2. Why the numerator/denominator mismatch existed

`resolve_simulated_floor_area()` (`parser.py:362-435`) sums `Floor Area x Zone Multiplier x Zone
List Multiplier` from the `.eio` for every zone with `Part of Total Building Area = Yes`. The
lighting/equipment loop summed `df[df["variable_name"] == var_name]["value"]` with no per-zone
weighting at all — a plain `.sum()` over the raw hourly rows. A multiplier-5 zone therefore
contributed 1x its energy against 5x its area in the denominator, undercounting the EUI.

## 3. Blast radius (unchanged from §5 fact 6 of the plan)

Zone multipliers are written in exactly one module (`openubem/geometry/layout_assigner.py`,
`match_storeys()`, `:649`), which the `auto` production path never calls. Three run-4 `auto` fleet
IDFs were read directly and every `Multiplier` field is 1. **The adopted 153.8231 kWh/m² pooled over
8,153 buildings is untouched by this fix** — every zone_multipliers.get() lookup on that corpus
would return the default of 1.0 even if the map were populated, because there is nothing to look up.
