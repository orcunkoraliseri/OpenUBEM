## 4. Dependency decisions (pinned — do not re-litigate)

**4.1 — The remote shell is tcsh and that is the whole point of this item.** `_ssh` sends a single
argv string (§5.2), so `sshd` hands it to the **remote login shell** to parse. `Unmatched '.` is
**tcsh's own error text for a quote it could not close**. Every T01–T03 measurement is about
**tcsh's parse**, not about bash, not about EnergyPlus, not about the cluster's load.

**4.2 — The harness does not import `v12_cell_pipeline`.** Import it and you inherit its
module-level constants and any side effects, and a failed experiment becomes ambiguous. **Copy the
two functions' logic into the harness** (`REMOTE_HOST = "o_iseri@speed.encs.concordia.ca"`, the
probe f-string from §5.3, the `subprocess.run(["ssh", HOST, f"bash -lc '{cmd}'"], …)` form from
§5.2), so the harness reproduces the *transport*, byte for byte, and nothing else.

**4.3 — 🔴 Probe a remote directory that does NOT exist. This is load-bearing.** The probe opens
with `cd {dir}/out 2>/dev/null || exit 0` (§5.3). Against an **absent** directory, a shell that
parses the command successfully exits **0 immediately, having touched no file**. So:

- **success = exit 0, empty output** → the 23k-char command **parsed**;
- **failure = exit 1, `Unmatched '.`** → the command **did not parse**.

This gives a clean binary on the parse alone, with **zero filesystem work and zero compute on the
login node** — which is why this sweep is permitted at all. Pin the target as
`/speed-scratch/o_iseri/fleets/__open57_probe_nonexistent__` and **verify it is absent** (one
`ls` via the `_ssh` form) before the sweep and again after.

**4.4 — Sequential, capped, and logged verbatim.** One `ssh` call at a time, never parallel. **At
most 20 calls in the whole plan.** Log the **actual remote stderr text** for every call — never a
label like "failed". If any call returns something that is neither of the two outcomes in §4.3,
**stop and report**; do not retry in a loop.

**4.5 — 🔵 Conditional authorisation for the remedy (T04).** Implement the remedy **only if T02
finds a reproducible length threshold** — i.e. there is an N where short lists parse and long lists
do not, and it reproduces on a repeat call. **If the sweep is not reproducible** (same length gives
different answers across repeats), the fault is not a parse limit: **stop at CP-1, do not touch
`v12_cell_pipeline.py`, and report.**

**4.6 — The remedy is stdin, not remote-side enumeration.** Pinned because it is the only option
that **preserves the function's exact semantics**: `_remote_results_complete` must answer *"is every
one of these specific oids complete"*, not *"how many directories are complete"*. Having the remote
side enumerate `out/*/` would silently change the question. So:

- `_ssh` gains `stdin_data: str | None = None`, passed to `subprocess.run(..., input=stdin_data)`.
  **Default `None` preserves today's behaviour exactly**; every existing call site is untouched.
- `_remote_results_complete` sends the ids **newline-separated on stdin** and loops
  `while read o; do …; done`, keeping the command a few hundred characters at any fleet size.
- `grep -q PATTERN FILE` does not read stdin, so it cannot eat the id stream. Keep the file
  argument.

**4.7 — Chunking is the fallback, not the first choice.** If T05's tests show stdin does not work
over this transport, fall back to chunking the id list into batches of 200 and summing the counts —
same semantics, more ssh calls. **Report the switch at CP-2**; do not silently substitute it.

**4.8 — OPEN-58 is an audit, not a repair.** T06–T08 **measure** the blast radius. **No fix to
`open56_zone_volume_experiment.py` or any dependant is authorised by this plan**, and no published
CSV may be deleted, regenerated or edited. If an artifact is unsound, you **record** that; the
director rules on what happens to it.

**4.9 — Production EUI is `openubem/results/parser.py`'s `total_eui_kwh_m2`** (§5.6). It is the
reference for defect (b). Where you can recompute an artifact's EUI from a surviving `.sql`, use
`parse_building()`; **do not re-implement the formula.**

### T02 — Find the threshold

**What.** Bisect the id count between the largest count that parses and the smallest that does not.
Start at the pinned ladder **226 → 500 → 1,000 → 1,589**, then bisect to a **single-id resolution**.

**Why.** A sharp, repeatable boundary means the fault is **deterministic and length-dependent** —
fully understood, never needing another blind retry. A fuzzy or shifting boundary means it is not a
parse limit, and §4.5 then forbids the remedy.

**How.** Sequential calls, §4.4's cap of 20 total across the plan. Each call logged verbatim.

**How to test.** Reproducibility is the test: once the boundary N is found, call **N−1 three times
and N three times**. All three below must parse; all three at or above must fail with the same
verbatim stderr. Record the byte length at the boundary — **that number is the actual limit**, and
report it against 4,096 / 8,192 / 10,240 / 16,384 / 20,480 so the reader can see which buffer it
lands on.

### T03 — Establish that length, not content, is what breaks it

**What.** At the boundary length, vary the **content** while holding the length fixed: (a) the real
id list; (b) the same byte count made of one long single token; (c) the same byte count with the
two embedded double-quoted strings removed.

**Why.** Rules out a content-triggered parse bug — an unbalanced quote, a metacharacter — that
merely correlates with long lists. It also tells the remedy what to avoid.

**How.** Three calls at the boundary, three just below it. Same harness.

**How to test.** If all three variants flip at the same length, **length is the cause** and content
is irrelevant. If they flip at different lengths, **say so plainly and stop at CP-1** — the remedy
in §4.6 still helps, but the diagnosis is not complete and the record must not claim it is.

**T05 addendum 3 — director-diagnosed and fixed second cause, 2026-08-19 — RESOLVED**

Director's hypothesis: `_ssh`'s `subprocess.run(..., text=True, input=stdin_data)`
wraps the child's stdin in a `TextIOWrapper(newline=None)`, which on Windows rewrites
every `LF` to `CRLF` on write — so the remote `while read o` loop was receiving
`way_123\r` (trailing carriage return baked into the id), and `[ -s "$o/eplusout.sql" ]`
never matched a real path. `n` stayed 0 regardless of how many buildings were actually
complete. This explains every observation to date: Call A (`GOT=1589`) never used `$o`
as a path, so it was blind to the corruption; anything downstream that used `$o` in a
file test failed silently.

**Verified locally first, zero cluster contact**, exactly as instructed:
`subprocess.run([...], input='a\nb\n', text=True, capture_output=True)` from a plain
child that echoes `repr(sys.stdin.buffer.read())` printed `b'a\r\nb\r\n'` — hypothesis
confirmed before a single ssh call.

**Fix, in `_ssh` only** (`scripts/validation/v12_cell_pipeline.py:127-178`): when
`stdin_data` is given, `subprocess.run` is now called without `text=True`, with
`input=stdin_data.encode("utf-8")` (raw bytes, bypassing the text-mode newline
translation entirely), and `stdout`/`stderr` are decoded explicitly afterward
(`utf-8`, `errors="replace"`). The `stdin_data is None` path is untouched byte-for-byte
(`text=True, input=None`, identical to before) — every existing caller is unaffected.
Docstring updated to record both causes. `RemoteCommandError`'s raise-on-non-zero and
`allow_fail`'s timeout short-circuit are both preserved, with the timeout handler now
decoding `exc.stdout`/`exc.stderr` only when they come back as bytes.

**Tests** (`tests/test_v12_ssh_stdin.py`, now 11 total, run in the foreground, all
pass): added `test_ssh_sends_stdin_as_raw_bytes_not_text_mode` (pins that
`subprocess.run` receives `input` as `bytes`, not `str`, and that `text=True` is never
set on the stdin_data path), `test_ssh_decodes_bytes_stdout_stderr_explicitly`, and
`test_stdin_bytes_survive_a_real_local_subprocess_round_trip` — a real (non-mocked)
local child-process round trip proving bytes-mode stdin survives uncorrupted while the
same payload sent through `text=True` still corrupts (sanity check on the bug itself,
so this test cannot rot into a false positive if the platform's behaviour ever
changes).

**Confirming live call**, same 226 real `phaseE_er33_la_centre` ids and same directory
as the earlier 0/226 result, now through the fixed code: **`remote completeness probe:
225/226 complete`**. This is not merely non-zero — it is the *exact* historical figure
already on record for this fleet (register: `225/226 complete — la_centre (two resume
runs)`, §5.4), which independently corroborates that the fix recovers the correct
count, not an arbitrary one.

this stdin CRLF corruption) are fixed and verified live. No `-x`-style or remote-side
workaround was used; only `_ssh` was touched, exactly as instructed.
