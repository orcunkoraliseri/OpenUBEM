# RESULT — Deep-Research M10: Foundation-Model & LLM-based Imputation (the "AI" frontier)

This document presents a frontier scan and feasibility analysis of pretrained foundation models (such as TabPFN) and Large Language Models (LLMs) for zero-shot building attribute imputation in OpenUBEM. It evaluates their capability, computational cost, reproducibility, and critical provenance-emitting properties against OpenUBEM's architectural constraints.

## Part C — Synthesis (the frontier ruling)

### 1. The Frontier Ruling
We issue a **firm disqualification** for Large Language Models (LLMs) — both zero-shot prompting and retrieval-augmented variants — for core input imputation in OpenUBEM. They violate every key scientific constraint: they fail reproducibility (due to API drift and non-deterministic text generation), they fail provenance (they cannot auditably trace where a "fact" was learned), and they fail offline capability (requiring massive local GPU overhead or external API dependency). Most importantly, the existential risk of **hallucination/confabulation** makes LLM-generated building data unusable for scientific physics-based models where data integrity must be strictly audited.

Conversely, **Tabular Foundation Models (specifically TabPFN)** are the only AI frontier approach that passes the constraint check. Since TabPFN runs locally as a lightweight library (~20MB), utilizes pinned, open weights, is deterministic when the seed is locked, does not require target-tuning (zero-fitted-parameters), and outputs calibrated probability distributions, it is architecturally compatible. However, due to the **complete absence of building-domain validation** in the literature, TabPFN is ruled **NOT READY for production deployment** in the main OpenUBEM pipeline today. 

### 2. Experimental Operation of TabPFN
If the manager greenlights an experimental track to evaluate TabPFN, it must be operated under the following protocol:
*   **Pinned Weights:** The codebase must lock a specific, version-controlled set of TabPFN weights (e.g., `tabpfn-v1.ckpt`) to prevent model drift.
*   **Complete-Case Context:** TabPFN operates via in-context learning. To impute a missing target attribute for a set of buildings (e.g., `building:levels`), the imputer must feed the model a "context" of complete-case buildings from the same micro-neighborhood (e.g., within 1–2 km, matching building types) as the training set, and the incomplete records as the query set.
*   **Per-Value Confidence:** The imputer must extract the entropy of the posterior class probabilities emitted by TabPFN. If the entropy exceeds a pre-defined threshold (indicating low-confidence classification), the value must fall back to a classical statistical baseline.
*   **Provenance Logging:** Every value generated by TabPFN must carry the Tier-A flag `TABPFN_IMPUTED` along with the numerical confidence score (e.g., max class probability).
*   **Target Inputs:** TabPFN should only be evaluated on MAR geometric/semantic inputs (`building:levels`, `use_class`, `footprint_area_m2`). It **must never** be used to impute physics-based parameters (e.g., HVAC COPs, U-values) as these represent structural gaps that do not correlate with spatial-geometric features in a way a generic tabular transformer can physically infer.

## CONFIDENCE AND CAVEATS

*   **Rapid Frontier Movement:** The tabular foundation model space is accelerating rapidly. Models like TabFM (Google Research, 2026) and TabPFN v2/v2.5 address the sample size ($N > 10,000$) and feature count limits of TabPFN v1. However, many of these are preprints or closed-weights models, which violates the OpenUBEM reproducibility constraint.
*   **Absence of Domain Literature:** There is a complete lack of empirical benchmarks comparing TabPFN to classical estimators (MICE, MissForest, KDE) specifically for building energy model input variables.
*   **Context Window Limitations:** Because TabPFN is a transformer that processes the observed training set inside the context window, it scales quadratically ($O(N^2)$) with the number of context buildings, making it slow and memory-intensive for large city-scale datasets ($N > 100,000$) unless local spatial clustering is applied first to partition the inputs.
