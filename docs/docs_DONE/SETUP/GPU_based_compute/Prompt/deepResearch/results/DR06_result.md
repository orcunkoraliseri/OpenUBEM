## 1. Executive Summary

OpenUBEM Step 6 computes raster urban microclimate fields at ~1 m resolution over km²-scale domains (`1000 × 1000` to `2000 × 2000` pixels) across hourly weather series (up to 8,760 hours/yr). Inspecting OpenUBEM's existing CPU implementation reveals that **two distinct bottlenecks** dominate runtime, while the remaining modules are straightforward memory-bound 2D tensor kernels:
1. **Static SVF & horizon angles (`svf.py`):** Dense integer pixel sweeps (`d = 1..max_radius_px`) across `N_az` azimuths (32–36) perform `~45,000`–`90,000` full-grid `arctan2`/`fmax` sweeps on `1–4 M` pixels. Notice that `shadow.py` already avoids re-marching buildings per hour by interpolating the cached `(N_az, H, W)` `horizon_angles` array in `O(1)` per hour.
2. **Dynamic vegetation beam transmission (`shadow.py`):** Unlike buildings, canopy DSMs (`cdsm`/`tdsm`) are re-marched densely from `d = 0` to `canopy_top` for every sunlit hour (`~4,380` hours/yr).
3. **Hourly radiation budget, MRT (`mrt.py`), and 210-term UTCI (`utci.py`):** Element-wise 2D grid algebra executed up to 8,760 times per year. (`solar.py` is a 1D vector over 8,760 timestamps and stays sub-millisecond on CPU.)

## 2. Q1 — Existing GPU Tools & Repositories

### Key Findings
- **SOLWEIG has three active GPU/high-performance re-implementations** as of 2026:
  1. **`nvnsudharsan/SOLWEIG-GPU`** (PyTorch, GPL-3.0, JOSS 2026): Supports CUDA, ROCm, Intel XPU, Apple Silicon MPS, and CPU fallback; uses spatial tiling for city-scale grids. Measured **25×–41× speedup** on an NVIDIA RTX A6000 vs CPU workstation for 1,000²–2,000² grids (`1,187 s → 47 s` at 1,000×1,000; `6,487 s → 158 s` at 2,000×2,000). Its sister global infrastructure **GLIDE-SOL** (Zonato et al., *GMD* 2026) measured **5.1× wall-clock speedup** on an NVIDIA A100 40 GB (`254 s`) vs CPU-only mode on the same node (`1,285 s`) for a 24 h Dortmund run at 2 m (`3,129 × 3,113`).
  2. **`zetingli/SOLWEIG-CUDA`** (CuPy + custom CUDA kernels, GPLv3+): NVIDIA-only, keeps geometry/SVF resident on GPU with async disk writes. Claimed/reported benchmark on Windows 11 (i9-13900K + RTX 4090 24 GB) for a Dublin `2,000 × 2,000` 1 m tile: **~2.7 s** for 1 day (24 h) and **~21 s** for 30 days (720 h), reported as **~4,000×** faster than QGIS/UMEP 4.1.1 CPU, **~100×** faster than `SOLWEIG-GPU`, and **~50×** faster than `GLIDE-SOL 0.1.1`.
  3. **`UMEP-dev/solweig`** (Rust + PyO3 + `wgpu` compute shaders, GPL-3.0): Official UMEP team rewrite (`v0.1.0` beta series, active 2025–2026) targeting cross-vendor GPUs (Metal/Vulkan/DX12/WebGPU via `wgpu`) plus multi-core Rust CPU and automatic tiling.
- **Accelerad (`nljones/Accelerad`) is stale/unmaintained (>2+ years inactive):** Last major release was **v0.7 beta in April 2019** (OptiX 6.0 / CUDA 10.0, Radiance 5.3 parity). No 2020–2026 releases exist; users rely on driver workarounds. While its published speedups (**7×–100×** over CPU Radiance `rpict`/`rtrace`) are historically important, it should **not** be adopted as a dependency for modern CUDA/Windows or Apple Silicon workflows.
- **Ladybug / Honeybee:** Core Radiance ray tracing remains CPU-bound (or optionally routed to legacy Accelerad), while **`ladybug-tools/honeybee-radiance-postprocess`** uses **CuPy** (NVIDIA CUDA only) to accelerate post-processing of Radiance annual daylight/irradiance matrices.
- **PALM-4U / PALM:** Uses **OpenACC** directives (`nvfortran -acc`) for experimental NVIDIA GPU execution; however, GPU support in PALM focuses primarily on the dynamical core and FFTs, and complete GPU porting of its 3D **Radiative Transfer Model (RTM 3.0)** remains limited/experimental (`UNVERIFIED` whether RTM 3.0 itself runs fully on OpenACC in current releases).
- **ENVI-met (Negative Result):** Core microclimate solver (`envicore_console.exe`) is **CPU-only** (multi-core CPU parallelism restricted to Business/Science licenses; Basic/Student single-core). It has **no native CUDA or OpenCL GPU acceleration**.
- **CityFFD:** Native **CUDA C++** (+ multi-GPU MPI/NCCL) urban LES airflow & temperature solver for city-scale domains (used to train FNO ML surrogates); primarily a CFD/aerodynamics solver rather than a raster SVF/UTCI tool.
- **VoxCity (`kunifujiwara/VoxCity`):** Actively maintained (2025–2026, ~618 stars, MIT) Python 3D voxel urban framework with an optional **Taichi** GPU module (`voxcity[gpu]` / `voxcity.simulator_gpu`) for solar irradiance, SVF, and Green View Index.
- **SEBE & GPU-DSRM:** UMEP's **SEBE** (Lindberg et al., 2015) is CPU-based in QGIS; research variants address viewshed/memory bottlenecks via GPU-accelerated raster/viewshed compression or **GPU-DSRM** (CUDA + ray tracing / back-face detection, reported **~45×** speedup over sequential CPU baseline on multi-building test beds).
- **pvlib-adjacent GPU projects (Negative Result for `pvlib` itself):** `pvlib-python` is CPU-only (NumPy/pandas/SciPy) with no native GPU backend; GPU-accelerated solar geometry/physics efforts live in separate JAX/PyTorch projects such as **`jax-solar`** (NeuralGCM TOA solar radiation in JAX) and **`dPV`** (differentiable solar-cell simulator in JAX).
- **NVIDIA Warp / OptiX ray-tracing projects:** **`NVIDIA/warp`** (Apache-2.0, ~7,100+ stars, active 2026 releases v1.17–v1.19) + **`NVIDIA/warp-optix`** (Apache-2.0/BSD-3-Clause) provide Python-authored OptiX BVH ray queries (`wo.accel_query_ray()`) and path tracing; specialized CUDA/OptiX solar ray tracers like **SolaRT** exist for spacecraft meshes.

## 3. Q2 — Algorithms & Complexity at km² @ 1 m Scale

Target domain sizes:
- **1 km² @ 1 m:** `H × W = 1,000 × 1,000` (`N_px = 10⁶` cells; max diagonal `R_max = ⌈√(H²+W²)⌉ = 1,415` px).
- **4 km² @ 1 m:** `H × W = 2,000 × 2,000` (`N_px = 4 × 10⁶` cells; `R_max = 2,829` px).

### 3.1 Sky-View Factor (SVF) on a 2.5D Height Raster
1. **Horizon-Angle Vectorized Sweep (SOLWEIG / Zakšek et al. 2011 / OpenUBEM `svf.py`):**
   - Marches `N_az` azimuths (typically 32–36) out to `R_max` (or capped radius `R_cap`, e.g., 200–500 m depending on tallest structure) computing `γ_k = max_d atan2(DSM(p + d·u_k) - z_obs, d·Δx)` and `SVF = (1/N_az) Σ cos²(γ_k)`.
   - **Why dense integer stepping matters:** As documented directly in OpenUBEM's `svf.py` docstring, geometric/log distance stepping skips thin walls at oblique angles and created up to **0.33 SVF error** at `H/W = 0.5`, whereas dense 1-pixel integer stepping matches the analytic canyon gate to `< 0.005`.
   - **GPU behavior:** Extremely regular, branch-free 2D array indexing (`O(N_az · R · H · W)`). Notice a crucial GPU optimization: the `svf.py` NumPy loop allocates a `(H, W)` temporary array at **every** `(k, d)` step (`45,280` kernel launches for `1000²`), whereas a single fused GPU kernel (or batched/unrolled `d` chunk inside a custom kernel / compiled graph) keeps `max_angle` in registers and streams `d` reads through L2/texture cache, cutting VRAM traffic by >10×.
   - **Sweep-line / 1D monotonic stack alternative (`UNVERIFIED` exact speedup on GPU):** For exact axis-aligned/discrete Bresenham lines, 1D upper-hull horizon scanning reduces `O(R · H · W)` to `O(H · W)` per azimuth via a stack, but the stack-based control flow diverges across GPU warps and is generally awkward compared to parallel tiled reads on GPUs unless mapped to 1D scanlines.
2. **Ray Casting / Monte Carlo Hemispherical Sampling (2.5D DDA or 3D BVH):**
   - Fires `K` hemisphere rays (e.g., 145 Tregenza patches or `K = 64–256` cosine-weighted / stratified rays) per pixel.
   - On a 2.5D raster, 2D DDA / ray marching stops at first intersection (`DSM > z_ray`), giving average path length `< R_max` in dense canyons, **but** suffers severe warp divergence when adjacent threads hit walls at `d = 3` vs sky at `d = 500`. On 3D triangle meshes with hardware RT cores (OptiX / Metal RT), BVH traversal handles `O(log M)` scene complexity naturally and supports overhangs/non-2.5D geometry.
3. **Shadow-Volume Projection (Rasterized Solar-Dome Stencil / Shadow Maps):**
   - Projects building prisms across `K` discrete sky patches via rasterization / shadow mapping (`O(K · V_tri)` + fill). Fast for coarse sky discretization (`K = 145`), awkward for smooth per-pixel `horizon_angles` caching needed by OpenUBEM's `shadow.py`.

### 3.2 Hourly Shadows on DSMs (`shadow.py`)
- **Horizon-Stack Interpolation (OpenUBEM current building algorithm):** Reuses the precomputed `(N_az, H, W)` `horizon_angles` stack via linear interpolation between two bracketing azimuths (`O(H · W)` per hour, zero marching!). On GPU this takes **sub-millisecond** per hour for `1000 × 1000`.
- **Per-Hour Ray Marching (current vegetation `cdsm`/`tdsm` path):** For `~4,380` daytime hours/yr, marches `d = 0..R_veg_max` where `R_veg_max = ⌈(max(cdsm) - min(z_obs)) / (res · tan(alt))⌉`. For `max(cdsm) = 25 m`, `alt = 10°`, `R_veg_max ≈ 142 px` (much smaller than `R_max = 1,415`, yet at `alt = 1°` it still reaches `1,432 px`). On GPU, executing a fused kernel across `B` hours simultaneously (or tiled in `(H, W)`) eliminates the `4,380 × 150+` Python loop overhead.
- **Shadow Volumes (Stencil):** Unsuited to raster DSMs and Beer-Lambert semi-transparent tree crowns; requires polygonal extrusions and suffers heavy overdraw.

### 3.3 View Factors for Building Surfaces & Irradiance with Reflections
- **Building Surface View Factors:**
  - *Hemicube:* Rasterizes 5 faces of a half-cube per patch (`O(N_patch · N_tri)`), suffers aliasing on small/grazing facets and scales poorly to `10⁵` urban facets.
  - *Monte Carlo Ray Tracing (MCRT) on BVH (OptiX / Mitsuba 3):* Fires `N_rays` (e.g., `10³–10⁴`) cosine-weighted rays per surface patch (`O(N_patch · N_rays · log M)`). Naturally handles arbitrary 3D geometries, concavities, and stochastic error control (`∝ 1/√N_rays`), and runs natively on RT cores.
- **Irradiance with Reflections:**
  - *SOLWEIG / OpenUBEM 6-directional bulk reflection (`mrt.py`):* Uses isotropic/SVF-weighted wall & ground albedo terms (`O(H · W)` per hour). Fast, matches standard SOLWEIG physics, no inter-building ray bounce.
  - *SEBE multi-bounce / Radiance-style 2-phase or 3-phase (`rfluxmtx` / `rcontrib`):* Precomputes a static sky/view transport matrix `T` (e.g., `N_sensors × 145` Tregenza/Reinhart patches) via GPU ray tracing (`O(N_sensors · N_rays · B_bounces · log M)` once), then evaluates **all 8,760 hours in seconds** via a single matrix multiply `E = T @ S_sky` (`O(8760 · 145 · N_sensors)`) in PyTorch/CuPy (`honeybee-radiance-postprocess` pattern).

| **MRT + UTCI (`mrt.py`, `utci.py`)** | 6-dir SOLWEIG + 210-term Bröde polynomial | `O(T · H · W)` (~250 FLOPs/px/hr) | ~10–15 intermediate `(H, W)` grids = **40–60 MB** (`1000²`) / **160–240 MB** (`2000²`) in `float32`. | **Optimal** (100% element-wise SIMD, fuseable with `torch.compile` / CuPy / Taichi). | `mrt.py` nighttime $T_{mrt}$ under-predicts by 2–10 °C vs measurements (Gál 2020, documented in `mrt.py`). Check UTCI `float32` accuracy vs `float64`. | Kamath et al. (2026); Bröde (2009); OpenUBEM `mrt.py`/`utci.py` |

*(Memory note: Total `45,280` `1000²` `float32` views without fusion does not allocate extra memory if reduced in-place, but naive PyTorch/CuPy expressions like `np.degrees(np.arctan2(window - z_obs, d * res))` allocate 4–6 temporary `4 MB` (`1000²`) or `16 MB` (`2000²`) buffers per step—making kernel fusion or `torch.compile`/custom kernels critical for speed.)*

## 4. Q3 — Python GPU Framework Fit (Apple Silicon macOS vs Windows NVIDIA)

### Verdict on Framework Fit
- **For Step 6 raster microclimate (`svf.py`, `shadow.py`, `mrt.py`, `utci.py`):** Use **`array-api-compat` + PyTorch** (with `float32` on MPS/CUDA, `cpu` fallback), optionally adding a **CuPy `RawKernel` fast-path** strictly for Windows/Linux NVIDIA workstations for the two dense marching loops (`svf.py` horizon sweep and `shadow.py` canopy march). This delivers a **single pure-Python source tree** testable on M2 Pro (`mps`), runnable out-of-the-box on Windows (`cuda`) via PyTorch, and unlockable to `SOLWEIG-CUDA`-class speed (`RawKernel`) on Windows NVIDIA without duplicating business logic.
- **For optional 3D ray-traced E+ shading / view factors:** Use **Mitsuba 3** (`metal_*` on Mac, `cuda_*` on Windows) if single-code-path Mac+Windows GPU ray tracing is required, OR **`NVIDIA Warp` (`warp-optix`)** if 3D ray tracing is run exclusively on the Windows NVIDIA workstation (CPU fallback on Mac).

### 5.2 Coupling Workflows & Published Accuracy / Runtime Evidence

| Workflow | Mechanism | Published Accuracy & Runtime Evidence |
|---|---|---|
| **A. Native E+ GPU `PixelCounting`** | `ShadowCalculation` → `Shading Calculation Method = PixelCounting` (`Pixel Counting Resolution = 512`), keeping `Shading:Building:Detailed` context geometry in IDF. | **Hoover & Dogan (2017, IBPSA BS2017):** GPU pixel counting achieved ~**2× speedup** on average for standard models and substantially higher scaling on complex urban/concave geometries, with sunlit-fraction accuracy within **~0.01** of analytical polygon clipping. Requires an active OpenGL/GPU context on the host running E+ (otherwise E+ logs a warning and silently falls back to CPU `PolygonClipping`). |
| **B. External GPU/Ray-Traced Precompute → `Imported` (`Schedule:File:Shading`)** | 1. Omit `Shading:Site:Detailed` / 20 m context buildings from IDF (or disable via `Imported`).<br>3. Set `ShadowCalculation` `Shading Calculation Method = Imported` and supply CSV in `Schedule:File:Shading`. | **Bognár, Loonen & Hensen (2021, *J. | **C. | **D. ### 5.3 Critical Pitfalls in External E+ Shading Coupling
1. **Sign Convention & Beam vs Diffuse Semantics:** `Schedule:File:Shading` and `External Shading Fraction Schedule Name` expect **sunlit fraction** (`1.0` = unshaded, `0.0` = fully shaded), *not* shade fraction (`1 - sunlit`). They govern **direct beam** sunlit area; **sky diffuse** and **ground-reflected diffuse** shading in E+ are NOT automatically driven to zero when `sunlit = 0` unless sky diffuse obstruction / view factors are handled consistently (and beware that removing `Shading:*` context surfaces from the IDF causes E+ to treat the sky as unobstructed (`SVF ≈ 0.5` for vertical walls) for sky diffuse & longwave exchange unless `SurfaceProperty:SurroundingSurfaces` or `SimpleSkyDiffuseModeling` adjustments are supplied!).
2. **Loss of Context Solar Reflections & Longwave Obstruction:** If 20 m context buildings are stripped from the IDF and replaced *only* by `Schedule:File:Shading`, E+ loses both `FullExteriorWithReflections` bounce radiation from neighbor facades and longwave blocking (cooler/warmer neighbor walls vs cold clear sky). Use `SurfaceProperty:SurroundingSurfaces` (with GPU-computed surface view factors + neighbor surface temperatures from OpenUBEM/T13) if longwave accuracy matters.
3. **Exact CSV Schema & Timestep Alignment:** `Schedule:File:Shading` requires row counts matching the simulation `Timestep` and year length (`8760` or `8784` × `TimestepsPerHour`), exact surface-name column headers, and matching DST/solar-time alignment with the EPW weather file. Mismatches cause fatal errors or silent `1.0` defaults.
4. **Conflicting `Shading:*` Objects:** Leaving 20 m context `Shading:Site:Detailed` surfaces in the IDF alongside `Imported` or `Scheduled` can create inconsistent diffuse shadowing or wasted initialization; keep self-shading geometry clean and document explicitly which obstructions live in the IDF vs the CSV.
5. **Daylighting Controls Mismatch:** If `Daylighting:Controls` is enabled in E+, `Imported` sunlit fraction gates direct beam illuminance through windows while internal daylight factors still compute sky diffuse assuming IDF geometry.

## 6. Q5 — Concrete Recommendation for OpenUBEM

### 6.1 Porting OpenUBEM Step 6 Hotspots (`svf.py`, `shadow.py`, `mrt.py`, `utci.py`)
1. **Backend Architecture (`xp` via `array-api-compat` + PyTorch):**
   - Refactor `svf.py`, `shadow.py`, `mrt.py`, and `utci.py` to accept/dispatch an array backend (`cpu` NumPy, `torch` on `mps` for M2 Pro dev, `torch` on `cuda` for Windows workstation) using `array-api-compat` and a centralized device/dtype helper (`dtype = torch.float32` on `mps`; configurable `float32`/`float64` on `cuda`/`cpu`).
   - **Pre-port verification gate:** Run OpenUBEM's existing unit/analytic-canyon tests (CP-1 / CP-2 / E-UTCI-04) in **`float32`** vs `float64`—especially `_brode_polynomial_offset` in `utci.py` (`d_tmrt^6` up to `70^6 ≈ 1.18e11`) and `svf.py` (`arctan2(window - z_obs, d * res)`).
2. **Algorithmic & Memory Optimizations (High ROI before/alongside GPU):**
   - **`svf.py` (Primary bottleneck):** Do **not** remove dense 1-px stepping (per `svf.py`'s own finding, geometric spacing fails the analytic canyon gate), **but** bound `max_radius_px` dynamically when possible (`R_eff = min(diag, ceil((max(dsm) - min(z_obs)) / (res * tan(gamma_min))))`, e.g. `gamma_min = 1°–2°` or domain horizon cap) and **tile spatial domains** (`e.g. 512 × 512` with halo) if domains exceed `2000 × 2000` to keep peak VRAM < 1–2 GB.
   - **Windows NVIDIA Fast Path (Optional Phase 2):** Once `array-api-compat` + PyTorch runs end-to-end on Mac MPS and Windows CUDA, add an optional **CuPy `RawKernel`** backend (~60 lines of CUDA C) exclusively for:
     1. `compute_horizon_angles_cuda`: fuses the `d = 1..max_radius_px` loop per `(az, pixel)` in registers so `45,280` temporary grid allocations collapse to **zero** (`SOLWEIG-CUDA` insight: this is why `SOLWEIG-CUDA` outperforms naive PyTorch tensor loops by ~10–100×).
     2. `_vegetation_transmission_cuda`: fuses the `d = 0..R_veg_max` Beer-Lambert loop with per-pixel early exit `ray_h > canopy_top_local` (impossible in whole-grid vectorized PyTorch/NumPy).
   - **`shadow.py` buildings:** Keep the current `O(1)` `_building_shadow_from_horizon` lookup! Simply run the azimuth interpolation on GPU alongside `mrt.py`.
   - **`mrt.py` & `utci.py`:** Keep fully on GPU in `float32` for all hours, batching chunks of hours `(B, H, W)` (e.g., `B = 24` or `168` hours at `1000 × 1000` ≈ 100–700 MB) to saturate GPU bandwidth and avoid 8,760 Python dispatch overheads, writing out aggregated comfort statistics or compressed GeoTIFFs asynchronously.

### 6.2 Optional GPU Shading Precompute for EnergyPlus (Phase 2/3)
1. **First check whether external precompute is needed:** EnergyPlus 23.1 already ships `ShadowCalculation` → `PixelCounting` (GPU OpenGL). Benchmark `PixelCounting` (with `Periodic` update frequency = 20 days vs `Timestep`) on the Windows workstation first (covered in DR02).
2. **When to build OpenUBEM's GPU E+ precompute:** If 20 m-context neighborhood models still spend >30–50% of E+ runtime in `Initializing Solar Calculations` / `PolygonClipping` (or fail OpenGL `PixelCounting` in headless/containerized Windows runs, or require tree-canopy / LiDAR shading that E+ cannot model natively):
   - Use **Mitsuba 3** (`cuda_scalar` on Windows, `metal_scalar` on M2 Pro) to cast `1` (or `5×5` grid) beam rays per exterior building surface centroid/sub-grid × ~4,380 sunlit hours against the merged 3D context + building BVH (`O(N_surf · 4380 · log M)` — seconds on RTX / Apple RT cores).
   - Export hourly sunlit fractions to CSV and inject into E+ via **`ShadowCalculation` (`Shading Calculation Method = Imported`) + `Schedule:File:Shading`**, stripping the 20 m context `Shading:Site:Detailed` surfaces from the IDF.
   - **Important accuracy guard:** Because removing context `Shading:*` surfaces changes E+'s sky diffuse & longwave view factors, also compute per-facade `Sky View Factor` (`SVF_facade`) in the same Mitsuba 3 pass and populate **`SurfaceProperty:LocalEnvironment` → `SurfaceProperty:SurroundingSurfaces`** (with sky/ground/context view factors) when thermal longwave accuracy in dense street canyons is required.
