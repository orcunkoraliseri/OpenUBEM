## 6. GPU Strategy Critique (§3.1)

### 6.1 Stage B (PyTorch Eager Python Time Loop) Will Be Severely Launch-Bound on MPS
- **Arithmetic:** One year (`105,120` run-period steps + `~1,700` warm-up steps $\approx 106,800$ steps) × (`~5` damped inside-surface iterations × `~7` tensor ops + `~30` window/convection/BDF3/psychrometric tensor ops $\approx 65\text{ ops/step}$) = **`~6.9 million` kernel dispatches per batch**.
- On macOS PyTorch **MPS**, eager Python + Objective-C `MPSGraph`/Metal command-encoder dispatch costs **~15–35 µs/op** (`torch.compile` on MPS still suffers graph breaks and poor loop fusion). Thus $6.9 \times 10^6 \times 22\text{ µs} \approx \mathbf{150\text{–}240\text{ s}}$ of pure host dispatch wall time — **synchronous with batch size up to $B \approx 5,000$**. At $B = 400$ (the certified EU campaign size in M1/M2!), 12-core CPU E+ (once the sizing bug is fixed: `70–105 s`) will **beat Stage B on MPS**.
- On **Windows CUDA**, eager Python dispatch (~6–10 µs/op) still wastes `40–70 s`, *unless* you capture **one 288-step day** inside a `torch.cuda.CUDAGraph` (with fixed iteration counts and masked updates) and replay that graph 365 times (`< 0.2 s` launch overhead) — an escape hatch MPS does not have.
- **Fix:** Do not gate Stage C behind "only if M2 is launch-bound" — **it is guaranteed launch-bound on MPS**. Keep Stage B minimal (a thin tensor verification bridge, plus `CUDAGraph` per-day capture on CUDA) and budget Stage C into the core Mac milestone.

### 6.2 Custom Metal / CUDA Kernels, OS Watchdogs (TDR), Register Spilling, and Chunking Design
1. **`torch.mps.compile_shader` vs. MLX `mx.fast.metal_kernel`:**
   - Both compile Metal Shading Language (MSL) compute kernels and are viable for fused time-stepping, **subject to three Apple Silicon hardware constraints**:
     - **31-buffer argument table limit (`[[buffer(0..30)]]`)** on Apple GPU Families 7–9 (M1–M4): passing individual `BatchSpec` fields as separate tensor arguments crashes Metal validation once args exceed 31. **Fix:** Pack all static building arrays into 1 flat SoA buffer, weather into buffer 1, schedules into buffer 2, persistent state (`[StateDim, B]`) into buffer 3, and chunk hourly output into buffer 4 (**5 buffers total**).
     - **Single-framework rule:** If `openubem[gpu]` already standardizes on PyTorch (also used by Phase 5 microclimate), use `torch.mps.compile_shader` on Mac and `torch.utils.cpp_extension.load_inline` (or CuPy `RawKernel`) on Windows, sharing a **single C/C++ header (`physics_core.h`)** compiled as both MSL (`#ifdef __METAL_VERSION__`) and CUDA (`__device__`)! Bringing in MLX solely for `mx.fast.metal_kernel` adds an unnecessary second array runtime on macOS only.
2. **GPU Watchdog / Timeout Limits (Monolithic 1-Year Kernel = Driver Crash):**

   - **macOS Metal (`IOGPUFamily` watchdog):** Default **~5 seconds** per `MTLCommandBuffer`; exceeding it aborts with `kIOGPUCommandBufferCallbackErrorTimeout` and freezes the desktop compositor.
   - While $B = 10,000$ S0 cells may finish a year in `< 0.5 s`, scaling to $B = 100,000$ scenario cells or S1/S2 multi-surface buildings pushes a monolithic 105,120-step kernel past `2.0–5.0 s`, crashing the GPU driver.
3. **Register Spilling Trap at S2 ("One Thread Per Building" Breaks Beyond S0):**
   - Spec §3.1 proposes *"one thread per building, state in registers/threadgroup memory"*. An Apple GPU thread has ~128–256 32-bit registers (`0.5–1 KB`) and 32 KB threadgroup RAM per threadgroup; CUDA caps threads at `255` 32-bit registers (`1 KB`).
   - For **S0** (`≤ 10` surfaces, modal state), dynamic state is `~50–70 floats` (`< 300 B`), which fits in registers **if** `ScriptF` (`10×10 = 400 B`) stays in cached device memory and all arrays use **Structure-of-Arrays `[Field, Building]`** (`Building` contiguous so 32 SIMD lanes coalesce).
   - For **S2** (`32–64` surfaces), `ScriptF` alone is `4–16 KB/building` and surface/modal states add `2–4 KB/building`. One thread per building **spills everything to local/device DRAM**, cutting throughput `10–30×`. **Fix for S2:** Map **1 SIMD-group / warp (32 threads) = 1 building** (each lane owns 1–2 surfaces; `ScriptF` matvec and zone `SumHA`/`SumHATsurf` reductions execute in registers via `simd_sum` / `__shfl_down_sync`).
4. **Required Chunking Design:**
   - **Warm-up:** Launch **1 day (`288` steps) per kernel call**. Check the per-building `CheckWarmupConvergence` mask after each day (max 25 launches = `< 0.5 ms` launch overhead) and stop as soon as all buildings in the batch converge (typically 2–6 days on S0 instead of spinning 25 days!).
   - **RunPeriod:** Launch **1 week (`2,016` steps) or 1 month (`~8,640` steps) per kernel call** (12–52 dispatches/year = `< 1 ms` total launch overhead, `5–150 ms` execution per chunk — 15–400× below Windows 2 s TDR and macOS 5 s watchdog), reading/writing the persistent `State[StateDim, B]` buffer across chunks and streaming small `744 × B` hourly chunk outputs back to CPU `float64`.
