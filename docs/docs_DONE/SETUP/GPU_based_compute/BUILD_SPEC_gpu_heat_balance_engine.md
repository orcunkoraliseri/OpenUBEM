## 0. What we are building (one paragraph)

A **GPU-native re-implementation of the EnergyPlus 23.1 algorithms for a declared, growing subset of IDF objects**. It runs **thousands of buildings at once**, with the whole year's time loop on the device. It is conformance-tested against EnergyPlus 23.1 on the same IDF and EPW.

It is **not**:
- a recompile of the EnergyPlus C++ for GPU;
- an RC approximation. The 7R2C ROM in plan Phase 3 stays a separate, coarser tier.

Any building that uses an object or field value outside the declared subset is **routed to EnergyPlus on the CPU (fail-closed)**.

### Why this shape (and not "port EnergyPlus to CUDA")

| Fact | Consequence |
|---|---|
| One building has too little parallel work. The European cell has 1 zone, 7 heat-transfer surfaces and 1 internal mass. A city building has tens to hundreds of surfaces. | A GPU parallelised *inside* one building stays idle. The parallel axis must be **buildings and scenario variants**. |
| E+ time stepping is sequential: predictor → corrector → history update. Warm-up and the inside-surface iteration are serial too. | Time stays a loop. Each building's small state walks the year on the device. |
| The E+ C++ is very large, uses global `EnergyPlusData` state, and has branchy HVAC iteration with plant loops and simulation managers. | A faithful source port is years of work and would still run one building per process. We **re-implement the equations** for the objects we use, reading E+ source as the specification. |
| EnergyPlus uses a 4-clause DOE licence (`/Applications/EnergyPlus-23-1-0/LICENSE.txt`): BSD-style clauses 1–3, no copyleft, plus clause 4 on the name. | Translating its algorithms is allowed. Files that translate E+ logic keep the E+ copyright notice, the DOE notice, clauses 1–4 and the disclaimer (a `LICENSE-ENERGYPLUS` file in `openubem/gpusim/`). Clause 4: never use "EnergyPlus", "E+" or "e+" in a package, product or feature name; `gpusim` is fine. Factual references ("conformance-tested against EnergyPlus version 23.1.0") are fine. No endorsement by DOE or the labs is implied (clause 3). This is unlike the GPL SOLWEIG repos (plan NG4). |

**Runtime (measured).** The cell takes **4.69 s wall** in E+ 23.1 on the M2 Pro under Rosetta (4.05 s elapsed per E+). The certified rerun has about 400 cells per repetition. IMP02 split this time on one cell (`ES.ME.SFH.04`, Bologna):
- **About 1.6 s of 4.2 s (38 %) is a full-year zone sizing pass whose result is never used.** Turning the sizing flags off gave the same annual heating to 8 decimals (32,069.768988 kWh). It is unused only because heating is `NoLimit` with no outdoor air; the router must keep that condition.
- Of the remaining 2.6 s, about 0.6 s is start-up, parsing, CTF/view factors, warm-up and output; about **2.0 s (78 %) is the real time loop**, about 15–19 µs per step.
- Native arm64 E+ 24.2 runs the same cell in 2.0 s (Rosetta costs about 1.27×).
- These are IMP02's measurements, not yet reproduced here. M0 reproduces the two that matter (as built vs sizing off).
- IMP03 ran 5 more EU-08 cells (ES, IT, GB; with and without doors and b<1 faces) with sizing off: zero difference on the annual total and on every one of the 8,760 hours. Not reproduced here.

**F1. Windows in the European campaign receive no solar gain. CONFIRMED in the source.** `european_box.py:113` sets `Sun_Exposure=NoSun` on the `Outdoors` host walls. Subsurfaces have no sun-exposure field and copy it from their host (`SurfaceGeometry.cc:5185`). The per-window solar output is registered only for sun-exposed windows (`SolarShading.cc:1253–1312`), hence "requested but not generated". `g_gl_window` is written into the IDF but has no effect.
- This is a **campaign-physics finding, independent of the GPU work**, and needs an owner ruling (D1).
- Turning sun on for the host walls would also add opaque solar absorption on those walls (absorptance 0.7) unless set otherwise.
- **Scope:** only the one-zone EU-08 box (`european_box.py`). The 3D EU-11 districts already set `SunExposed` on exterior walls (`scripts/run_eu_s2_campaign.py:1051`, checked).
- **IMP03 recommendation, option (c):** host walls `SunExposed`, `Material:NoMass` solar absorptance 0 on outdoor surfaces only (the floor keeps its value, or E+ stops with a severe error because window solar lands on the floor; found at M0 T04) (TABULA counts window solar only; IDD `\minimum 0`), window SHGC × 0.42 (TABULA shading 0.6 × (1 − frame 0.3); the non-perpendicular factor 0.9 is left out because E+ simple glazing already applies its own angular SHGC). IMP03 measured on 5 EU-08 cells: heating falls 8–41 % with (c); raw glass with absorptance 0.7 (option b) falls 18–69 %, which over-counts. Unverified here.
- For gpusim, S0 reproduces the run *as built*. S1 adds solar.

**F2. The internal mass stores about half the intended heat. NEW (IMP02), code facts confirmed.**
- `european_physics.py:57–100` sizes one 0.10 m concrete slab (162,000 J/m²K) so that area × capacity = 45 Wh/m²K × floor area.
- E+ holds **both** faces of an `InternalMass` at the inside-face temperature but exchanges heat with the zone through **one** face area. By symmetry the mid-plane is adiabatic, so only half the slab (0.05 m) charges: about **22.5 Wh/m²K** realised instead of 45.
- The IDD memo says the area is "the total surface area exposed to the zone air". IMP03 quotes the E+ 23.1 I/O Reference, `InternalMass` (§1.10.40, p. 325): "If both sides of the surface exchange energy with the zone then the user should input twice the area when defining the Internal Mass object."
- This is a campaign-physics question for the owner (D2), like F1. gpusim S0 reproduces the IDF *as built* either way.
- **Scope:** `add_european_internal_mass` is called by the EU-08 runner (`eu_cell_runner.py:376`) **and** the EU-11 district script (`scripts/run_eu_s2_campaign.py:2055`), both checked.
- **IMP03 recommendation, option (b):** area 2 × A_floor, slab stays 0.10 m (24 h effective capacity about 45 Wh/m²K at the face; doubling the thickness instead reaches only about 21 because the surface film limits it). Side effect measured by IMP03: the larger mass area changes interior view factors, so heating rises 0.5–2.3 % with no sun and changes −3 % to +1.5 % once solar is on. Unverified here.

**City and North-American path** (`openubem/idf/hvac.py`, `surfaces.py`): multi-zone geomeppy blocks, layered massive constructions, `Shading:Site:Detailed` context, and HVACTemplate PTAC, PSZ-AC, PSZ-HP, PVAV, VAV, FCU and WLHP with plants, plus refrigeration and DHW. That is where the 900 s tail runs are (plan §1). The PTAC/PSZ templates autosize every coil capacity and airflow and carry economizers (`hvac.py:190–299`).

## 3. Architecture

```
IDF (as written by OpenUBEM) ──ExpandObjects──▶ expanded IDF          archetype table
        │                                                                    │
        ▼  CPU, Python, float64                                              │
 [subset.py]   whitelist check ──fail──▶ EnergyPlus CPU path (unchanged)     │
        │ pass                                                               │
 [compile.py]  IDF ➜ BatchSpec  ◀───────── BatchSpec.from_records(...) ──────┘
               padded dense arrays per bucket: areas, U, CTF/modal coefs,
               OSC coefs, convection ids, ScriptF, centroid heights, ACH, setpoints
 [weather.py]  EPW ➜ per-timestep arrays shared by every building at a site
 [schedules]   Schedule:File/Compact ➜ timestep arrays (or hourly + index)
        │
        ▼  GPU, in chunks (warm-up: 1 day per launch; run period: 1 day–1 week per launch)
 [kernel]      per zone timestep, in E+ order (§3.0)
        │
        ▼  CPU
 [writer]      hourly sums ➜ float64 annual totals; Parquet for large sweeps;
               eplusout.csv-compatible columns kept for the existing extractors + provenance
```

For sweeps of 10k+ buildings, `compile.py` builds BatchSpec directly from the archetype table. Parsing 10k text IDFs in Python would cost more than the GPU run. Text-IDF parsing stays for validation and fallback.

### 3.0 Timestep order and constants (E+ 23.1, `AllCTF` path)

Per zone timestep:
1. **Weather.** EPW values mark the end of the hour. Step `ts` of 12 uses weights `ts/12` (this hour) and `1 − ts/12` (previous hour). On the first hour of an environment the "previous hour" is hour 24 of day 1. Humidity ratio and sky temperature are recomputed each timestep. Missing `IRHoriz` (≤ 0 or ≥ 9999) is replaced hourly by the Clark–Allen model (`WeatherManager.cc:3382`) before interpolation. `Schedule:File` with `Interpolate_to_Timestep=No` stays constant within the hour.
2. **Height lapse.** Each surface and the zone see `T_out − 0.0065·z·R/(R+z)` (`DataEnvironment.cc:102–107`), z = centroid height. The zone centroid excludes internal mass.
3. **Outside faces, once per step** (`CalcHeatBalanceOutsideSurf`): OSC faces from lagged `MAT`; outdoor faces with DOE-2 at zero wind (natural part only, no low-h clamp) and longwave split: sky weight `F_sky·√(0.5(1+cos tilt))`, the rest of the sky view to air, ground view at air temperature (`SurfaceGeometry.cc:355`).
4. **Inside convection, once before iterating**, from lagged surface and air temperatures. TARP with **−cos tilt** for inside faces (`ConvectionCoefficients.cc:7100`), clamped to `[0.1, 1e7]`. Re-evaluated only when iteration count > 0 and divisible by 30.
5. **Inside-surface iteration** (`CalcHeatBalanceInsideSurf2CTFOnly`): windows only on iteration 0; ScriptF interior exchange every iteration; opaque update with damping `IterDampConst = 5.0 W/m²K` (`HeatBalanceSurfaceManager.cc:7829`); stop when max change ≤ 0.002 K (`MaxAllowedDelTemp`), at least 1 and at most 500 iterations. Per-building convergence mask.
6. **Zone predictor**: load to setpoint ➜ ideal-loads Q (≥ 0, heat only), supply-temperature limit, enthalpy-based coil load.
7. **HVAC sub-stepping**: if the zone temperature change exceeds 0.3 K (`MaxZoneTempDiff`, `HVACManager.cc:332`), split the step into system sub-steps. Reported zone temperature is the sub-step mean.
8. **Zone corrector**: third-order backward difference on temperature **and** humidity ratio, written in difference form (§3.2).
9. **History shift**; accumulate per-hour sums.

Initialisation: surfaces and air at 23.0 °C (`HeatBalanceSurfaceManager.cc:7582–7584`). Warm-up repeats day 1, minimum 2 days in practice, maximum 25; loads test uses `max(load, 100 W)` (`HeatBalanceManager.cc:3475`); histories carry through warm-up into the run without reset.

### 3.1 Backends: one physics, three implementations

| Stage | Backend | Purpose | Runs on |
|---|---|---|---|
| **A** | NumPy float64, vectorised over the batch, Python time loop | **Executable specification.** Conformance against E+ is proven here. Its throughput is also measured (it is already a batched CPU engine). | Mac and Windows CPU |
| **B** | PyTorch, same structure, `device ∈ {mps, cuda, cpu}` | **Verification bridge only**: runs the shared `xp` physics on the GPU to catch device and float32 issues. Not a speed target. A per-step Python loop means about 2M+ launches per year, which is launch-bound on MPS. | Mac (MPS), Windows (CUDA) |
| **C** | Fused kernel run in chunks; state persists in a device buffer between chunks | **The speed target. Planned, not optional.** | Mac: Metal. Windows: CUDA. |

**Chunking (required).** One launch per warm-up day, with the convergence mask checked on the CPU between days. Run period: one launch per day to one week. Each launch must stay far under the Windows GPU timeout (2 s default) and the macOS command-buffer watchdog. Pack inputs into a few structure-of-arrays buffers (`[field, building]`, building index contiguous): static building data, weather, schedules, state, hourly output.

**Thread layout.** S0 and S1: one thread per building (state fits in registers; ScriptF in device memory). S2b: one SIMD group / warp per building is expected to be needed (decide from a register-pressure measurement at S2a).

**Framework (open, decided by a 1–2 day spike after M1).** Candidates:
- **PyTorch host + one shared C header** compiled as Metal (`torch.mps.compile_shader`) and CUDA (`load_inline` or CuPy `RawKernel`). IMP02's pick; also in our rev. 1 list.
- **wgpu-py / WGSL**: one shader for Metal and DX12/Vulkan, pip-only, no CUDA toolkit. IMP01's pick.
- Dropped: Taichi (maintenance risk), JAX (no Mac GPU, Windows needs WSL2), MLX (Mac only), NVIDIA Warp (no Metal backend).

Spike exit criterion: the S0 kernel step from Stage A runs on both machines from one source, and the float32 gate passes on 5 cells.

### 3.2 Precision

Apple GPUs have **no float64** in Metal. Stage A (float64) is the reference; Stage C runs float32 with these rules:
- Temperatures stored as deviations from 20 °C.
- `T_i⁴ − T_j⁴` always factored as `(T_i − T_j)(T_i + T_j)(T_i² + T_j²)`, in ScriptF and in exterior longwave.
- Third-order backward difference written in difference form (solve for the step change; history enters as differences), so a steady zone has exactly zero update.
- Energy summed per hour in float32 on the device, then annual totals in float64 on the CPU.
- **Conduction:**
  - **S0**: the single internal-mass CTF (6 terms) passes the float32 gate per IMP02's test. Keep direct-form CTF with coefficients rounded so their sums are preserved.
  - **S2a and beyond**: direct-form float32 CTF **fails** on an ordinary insulated wall (10 cm XPS + 25 cm concrete): the coefficients cancel to a net sum smaller than float32 resolution, giving about −29 % steady conduction error (IMP02, measured; consistent with the arithmetic). Use either a modal state-space form (diagonalised in float64 at compile time; steady conduction exact, all modes decaying) or double-single (float32 pair) accumulators. Choose at S2a with a test on the five thickest TABULA walls.
- Gate: float32 against the float64 reference (§4 table).
- On CUDA, float64 is available. Keep a `--fp64` switch for diagnosis; not the default.

### 3.3 Faithfulness rules ("bug-for-bug where it matters")

- Read the **E+ 23.1.0 source** (`NREL/EnergyPlus` tag `v23.1.0`) as the specification. Cite file and function in every routine. Files to start from:
  - `HeatBalanceSurfaceManager.cc`: outside and inside surface heat balance, OSC, iteration, history, initialisation;
  - `ZoneTempPredictorCorrector.cc`: third-order backward difference, predictor, corrector, humidity ratio;
  - `ConvectionCoefficients.cc`: TARP inside, DOE-2 outside, ISO 15099 window inside, exterior longwave coefficients;
  - `HeatBalanceIntRadExchange.cc`: approximate view factors, `FixViewFactors`, ScriptF;
  - `WindowManager.cc` and `HeatBalanceManager.cc`: SimpleGlazingSystem conversion and window heat balance;
  - `SurfaceGeometry.cc`: subsurface inheritance, internal mass, floor/roof flip, centroids, sky/air split;
  - `ZoneEquipmentManager.cc`: ventilation;
  - `HVACManager.cc`: system sub-stepping;
  - `PurchasedAirManager.cc`: ideal loads;
  - `WeatherManager.cc`, `DataEnvironment.cc`: interpolation, sky temperature, height lapse, solar (S1);
  - CTF generation (port to float64 Python for S2a);
  - `SolarShading.cc`: sun position and FullExterior distribution (S1).
- Reproduce E+'s **timestep ordering** (§3.0) and the **warm-up convergence test**. E+ hourly values are sums of the timestep values in that hour.
- Where E+ behaviour is odd but affects results (F1, F2, floor flip), reproduce it and note it.

## 4. Conformance harness (built before any kernel)

- Zone Mean Air Temperature, Zone Air Humidity Ratio;
- Surface Inside Face Temperature, Surface Outside Face Temperature;
- Surface Inside Face Convection Heat Gain Rate and Convection Heat Transfer Coefficient;
- Surface Inside Face Net Surface Thermal Radiation Heat Gain Rate;
- Surface Outside Face Convection Heat Transfer Coefficient and Thermal Radiation to Sky/Air/Ground Heat Transfer Coefficients;
- Zone Ideal Loads Zone Sensible Heating Rate;
- Zone Ventilation Sensible Heat Loss/Gain Energy;
- Site Sky Temperature, Site Outdoor Air Drybulb Temperature;
- `Output:Constructions` (CTF dump), the `.eio` warm-up information, and the `.err` (floor flip warning);
- for S1, Surface Outside Face Incident Solar Radiation Rate per Area and Zone Windows Total Transmitted Solar Radiation Rate.

Store them as Parquet under `tests/fixtures/gpusim/golden/` (small cells) with the IDF, EPW and E+ version hash. Cover at least one cell with a door, one with the thermal-bridge face, and one EPW with missing `IRHoriz` if any exists in the campaign. Also record the decision variants (IMP03, D3 advice) on the stress base: V14 internal mass area ×2 (D2 fix, still S0), V15 the D1 fix (option c in §1). **What "the same results" means.** For buildings that stay on EnergyPlus, results must be identical. For buildings run by gpusim, bit-identical results are not possible: a different summation order already changes the last digits, and the Mac GPU has only 32-bit floats. "Same" therefore means "inside the §4 gates", which are set far below any modelling uncertainty (0.05 % median annual heating for S0). At S0 almost every city building is routed to E+, so P3/P4 first prove that routing is fail-closed and corrupts nothing; their gpusim share grows rung by rung.

**Tolerances.** Stage A uses the same equations as E+ in float64, so a 0.2–0.5 % gap means a missing equation, not noise. Relative gates get an absolute floor so near-zero-heating cells do not fail by division. Single-step spikes from E+ branch thresholds (sub-stepping at 0.3 K, warm-up day count, TARP sign switch) are handled by a p99.9 gate plus a looser hard maximum.

| Quantity | S0 gate | S1–S2 gate |
|---|---|---|
| Stage A vs E+, annual heating, fleet median | ≤ 0.05 % or ≤ 0.02 kWh/m² | ≤ 0.15 % or ≤ 0.05 kWh/m² |
| Stage A vs E+, annual heating, fleet p99 | ≤ 0.2 % | ≤ 0.5 % |
| Stage A vs E+, annual heating, worst cell | ≤ 0.5 % or ≤ 0.05 kWh/m² | ≤ 1.5 % or ≤ 0.15 kWh/m² |
| Hourly heating over active hours (either engine > 1 W/m²) | CV(RMSE) ≤ 1 %, \|NMBE\| ≤ 0.1 % | CV(RMSE) ≤ 3.5 %, \|NMBE\| ≤ 0.3 % |
| Zone air temperature, all timesteps | p99.9 ≤ 0.03 K, max ≤ 0.25 K | p99.9 ≤ 0.10 K, max ≤ 0.60 K |
| Stage C float32 vs Stage A | annual ≤ 0.05 % or ≤ 0.01 kWh/m²; ΔT p99.9 ≤ 0.02 K, max ≤ 0.10 K (warm-up day count locked to Stage A in this test) | same |

A failure at any rung blocks that rung. It never loosens a tolerance silently: changes are made in this table, with a reason.

**What the speed-up should look like (estimates; M3/M4 measure it):**
- Rev. 1 assumed most of E+'s 4 s was overhead. **That was wrong.** Per IMP02's split, about 1.6 s is an unused sizing pass, about 0.6 s is start-up and output, and about 2.0 s is the real time loop.
- The fair CPU baseline is therefore **E+ with sizing off** (about 2.6 s per cell on 23.1 under Rosetta, 2.0 s on 24.2 arm64), run on all cores. For 10k S0 cells on the M2 Pro that is roughly 35–45 minutes.
- gpusim wins by removing per-step C++ overhead and running many buildings in lock-step. IMP02 estimates 10k S0 cells in about 5–15 s end to end on the M2 Pro (Stage C), i.e. one to two orders of magnitude over the fair baseline. **Unverified; M3 measures it.**
- **Payback depends on volume.** For the 400-cell EU rerun, the sizing fix alone brings 12-core wall time to about 1.5 minutes. gpusim pays back only for large sweeps (scenario × retrofit × weather × stochastic occupants, 10⁵+ building-years) or interactive use.

## 6. Package layout

```
openubem/gpusim/
  __init__.py
  LICENSE-ENERGYPLUS # E+ copyright, DOE notice, clauses 1–4, disclaimer
  subset.py          # rung whitelists (object types + allowed field values), router decision + reason
  compile.py         # expanded IDF or archetype records ➜ BatchSpec, bucketing by surface count
  weather.py         # EPW ➜ timestep arrays (E+ interpolation, Clark–Allen fallback, sky temp, solar for S1+)
  schedules.py       # Schedule:File/Constant (S0), Compact/Day/Week (S2a)
  ctf.py             # S0: internal-mass CTF; S2a: own float64 CTF generator (+ modal form if chosen)
  viewfactors.py     # approximate view factors, FixViewFactors, ScriptF (float64, once per building)
  physics/           # pure functions per equation, backend-agnostic via an `xp` array namespace
    convection.py    # TARP inside, DOE-2 outside, ISO 15099 window inside
    lwr.py           # ScriptF interior exchange, exterior sky/air/ground split
    window.py        # SimpleGlazingSystem layer and two-face balance
    surface_hb.py    # outside and inside face balance, damping, convergence
    zone_air.py      # 3rd-order backward difference (T and W), predictor/corrector, ideal loads, sub-stepping
    psychro.py       # Psy* functions used by S0
  backends/
    numpy_ref.py     # Stage A
    torch_batched.py # Stage B (verification bridge)
    kernel/          # Stage C source (shared header or WGSL, per the spike) + launch/chunk driver
  writer.py          # hourly ➜ float64 totals, Parquet + eplusout.csv-compatible output, provenance
tests/gpusim/        # unit (per-equation), cell, fleet conformance
scripts/gpusim/      # make_golden.py, bench.py
```

The physics functions are written once against an array-namespace argument `xp` (NumPy or torch), so Stages A and B share the equations. Stage C is checked against Stage A by the float32 gate.

## 7. Risks

| Risk | Mitigation |
|---|---|
| A hidden E+ detail breaks conformance | §3.0 lists the known ones with source lines. Per-equation unit tests against golden intermediates (§4). The E+ source is the spec. |
| float32 conduction error on thick walls | S0 is safe. S2a chooses modal form or double-single before any layered wall runs (§3.2). |
| GPU timeouts (Windows 2 s, macOS watchdog) | Chunked launches (§3.1); chunk length set from a measured per-chunk time with a 10× margin. |
| Register spill on multi-zone buildings | One SIMD group per building at S2b, decided from a measurement at S2a. |
| Warm-up day count differs per building | Per-building convergence mask, checked between 1-day launches. Converged lanes freeze. |
| Padding waste (different surface counts) | Bucket by surface count. S0 has one bucket. |
| Input compile slower than the kernel | `BatchSpec.from_records` from the archetype table for large sweeps. |
| Scope creep toward full E+ | Ladder stops at S3 if D4 drops S4. S5 is not planned. The router keeps E+ as the source of truth. |
| Campaign physics changes (F1, F2) after S0 is built | S0 reproduces the IDF as built; a ruling changes the IDF, and the same engine follows. S0 and S1 stay separately testable. |
| Not enough volume to pay back | Stated in §5. The sizing fix is the cheap win for the current campaign either way. |
