### Table 3 — Selection & isolation mechanics

| Question | Answer + source |
|---|---|
| **How does picking work at neighbourhood scale, and does it scale to hundreds of buildings without a frame-rate hit?** | For the `V06`-recommended three.js stack, picking uses `THREE.Raycaster` cast from the pointer through the camera, testing ray-mesh intersection. Three.js's raycaster is confirmed efficient against `InstancedMesh` — it tests the whole instanced mesh's bounding volume first, only descending to per-instance checks if the ray intersects, reducing typical checks from thousands of objects to well under 100 near the cursor (three.js forum / GitHub issue tracker discussion). OpenUBEM's per-building assets are **not** instanced (each building has distinct footprint/window geometry), so the default approach is `raycaster.intersectObjects(buildingMeshes, true)` against hundreds of individually-meshed buildings — three.js internally does bounding-sphere/box rejection before triangle tests, and picking only runs on click/hover (not every frame), so hundreds of buildings should not meaningfully affect frame rate. **GAP** — no published benchmark exists for IDF-derived, non-instanced building meshes specifically at OpenUBEM's scale (hundreds of buildings, dozens of triangles each); this is a synthesis extrapolation from general three.js picking behaviour, not a measured number, and should be pilot-tested. |
| **How does "isolate" interact with the LOD ladder — does isolating a building auto-trigger the `V04` drill-down, or are they independent?** | `RESULT_V04`'s recommended discrete-swap mechanic **bundles them**: on selecting a building, the viewer "queries the building's metadata... fetches and loads `{building_id}_lod3.glb`... unloads or hides `{building_id}_lod1.glb`." Selection and LOD drill-down are specified as the same action, not independent. This matches the peer-tool pattern in Speckle, where select → isolate → inspect is one conceptual workflow (even if isolate is a distinct button click there). **Recommendation for V08:** bundle isolate + drill-down into the single primary click for MVP; a separate "isolate-without-drill-down" affordance is deferred (Table 1). |
| **Can a surface (not just a building) be individually selectable given the geometry format from `V03`?** | **Yes, conditionally.** `V03` recommends **CityJSON** as the primary interchange format, which stores windows/doors as first-class `"Window"`/`"Door"` semantic surface types nested under their parent `WallSurface`, each independently addressable in the file. This must be gated by `RESULT_V04`'s Rule V04-RMG-01 resolution-mode check. |

This is a packaging tradeoff (bundle-everything vs. lazy-load-from-folder), not a hard block. |

## Part C — Synthesis (the interaction grammar spec)

### 1. The MVP interaction set (tied to the three.js API)

- **Orbit/pan/zoom** — `THREE.OrbitControls` bound to the camera + `renderer.domElement`; `target` set to the scene's bounding-box centroid on load; `minDistance`/`maxDistance` clamped to a neighbourhood-appropriate range so the camera cannot clip through roofs or fly to empty space [1].
- **Select/highlight a building** — `THREE.Raycaster.setFromCamera(pointerNDC, camera).intersectObjects(buildingMeshes, true)` on click; on a hit, apply an emissive/outline material override to the intersected building's root `Group` [3].
- **Neighbourhood → building LOD drill-down** — bundled into the same click as select (Table 3, Q2): on hit, load/reveal `{building_id}`'s LOD-B asset (CityJSON semantic surfaces including windows/doors, per `RESULT_V03`) and hide its LOD-N massing asset, per `RESULT_V04`'s discrete-swap spec [16].
- **Building → neighbourhood zoom-out** — an explicit "Back to neighbourhood" UI affordance (button or Esc key) that reverses the swap and recenters `OrbitControls.target` on the neighbourhood centroid. Commit to an **explicit action**, not an implicit scroll-zoom-out threshold, to avoid accidental asset unloads mid-navigation.

### 2. The drill-down trigger design

**Commit to CLICK on a building mesh, not a zoom/distance threshold.** Reasons:

1. OpenUBEM's discrete-swap LOD mechanic (`RESULT_V04`) is asset-based (two pre-built `.glb`/CityJSON payloads per building), not continuous tile streaming — there is no per-frame screen-space-error signal to hook a zoom-threshold to the way OGC 3D Tiles does natively in CesiumJS.
2. Click-to-select is the near-universal peer convention (`RESULT_V02` Table 2 — every listed tool supports "select").
3. A zoom-threshold trigger risks a jarring "auto-load storm" if multiple buildings cross the threshold simultaneously during a scroll-zoom near a dense block.

The reverse (zoom-out) is likewise an **explicit "back" action**, not an automatic distance threshold, for the same reason. `RESULT_V04` does allow an *optional* camera-elevation-based downgrade rule as a crowded-scene fallback (e.g. "if camera elevation > 500 m, force all buildings to LOD-N") — this prompt defers that specific rule to `V12` (performance/scale), since it is a scale-driven safety valve, not part of the core click-driven drill-down grammar.

### 3. Deferred list

| Interaction | Reason for deferral |
|---|---|
| First-person walkthrough | Low value for the primary "inspect the model" analysis task; requires custom collision/gravity work three.js does not provide out of the box (Table 2). |
| Isolate as a separate action from select | Folded into select/drill-down for MVP (Table 3, Q2); a standalone "isolate without loading detail" mode is redundant at MVP. |
| Section/clipping plane | Natively supported by three.js (`clippingPlanes`), so not a stack limitation — but only meaningful for the ~6% of the current fleet simulated in `zone` resolution mode (`RESULT_V04`); for the other ~94% it would expose an undivided slab. Low value given current fleet composition, and a misleading-display risk (Table 4, Q2) if not carefully gated. |
| Per-surface (window/wall) selection | Depends on an **unconfirmed** granularity guarantee from the CityJSON→three.js loader pipeline (Table 3, Q3 GAP) — a scale/feasibility risk, not yet a low-value call. |
| Measurement | Dominant concern is false-precision risk (Table 4, Q2); no UBEM peer tool (ubem.io/CEA/Torino) ships it — it is imported from the BIM/AEC tradition (Speckle/IFC.js), not a UBEM-viewer convention. |
| Map-tilt / MapLibre 2.5D camera | Pure stack limitation — three.js has no native map-tilt camera; only relevant if/when the `RESULT_V06` MapLibre-hybrid fallback is adopted for a geo-referenced basemap, not for the standalone-three.js MVP. |

### 4. What the chosen stack cannot do — flagged for `V10`/`V12`

- **True 3D-Tiles-style screen-space-error-driven LOD streaming** is not available in the chosen discrete-swap/CityJSON pipeline (three.js has no built-in equivalent). If the fleet grows to city scale (thousands of buildings) and click-driven discrete swap proves insufficient, **`V12` (performance/scale) will need to design a camera-distance-driven batch-downgrade rule on top of the in-memory CityJSON model** — there is no off-the-shelf streaming-LOD engine for a self-contained three.js/CityJSON artifact. None of `V02`'s peer teardown examples solve this in a directly reusable way: UMI uses full desktop CAD (no browser streaming concern at all), and 3DCityDB/Torino solve it via native 3D-Tiles streaming, a stack `V06` explicitly rejected as primary for OpenUBEM.
- **Section/clipping through a tile-streamed scene** (the prompt's own example of an infeasible combination) is moot for OpenUBEM since three.js — not CesiumJS/3D-Tiles — was chosen as primary; flagged only for completeness in case `V12` later revisits the CesiumJS/MapLibre-hybrid path for a very large city rollout.
- **Map-tilt-style navigation with true building-envelope fidelity simultaneously** — MapLibre's native camera is degraded to 2.5D extrusion geometry (Table 2); getting *both* the familiar map-tilt navigation *and* faithful window/roof geometry requires the three.js-inside-MapLibre custom-layer hybrid `RESULT_V06` describes, which is architecturally heavier than either stack alone. `V10`/`V13` should treat this as a deployment-complexity flag, not assume it is free.

## Confidence and caveats

- **Least evidenced:** picking-at-scale for hundreds of **non-instanced** building meshes (Table 3, Q1) and per-surface selection granularity through the CityJSON→three.js loader (Table 3, Q3) are both synthesis/extrapolation, not measured or directly demonstrated examples — no working public example of a CityJSON-derived, hundreds-of-buildings, per-surface-pickable three.js viewer was found within the search budget. Both are flagged `GAP` inline and should be pilot-tested before being locked into a PLAN.
- Section-plane and measurement precedents are drawn entirely from **BIM/AEC** tools (Speckle, IFC.js/web-ifc-viewer), not UBEM-specific tools — reasonable given the prompt's own instruction to ground these in BIM/AEC-viewer convention, but it means there is no direct UBEM-context validation that these two interactions are worth building at all (reflected in their "defer" priority).
- `web-ifc-viewer` (IFC.js) is confirmed **deprecated** by its own README, in favour of `@thatopen/components` — cited here only as evidence of the clipping-plane/measurement API pattern (`viewer.clipper.createPlane()`, `LengthMeasurement`/`AreaMeasurement` components), not as a library recommendation for OpenUBEM to depend on directly.
- MapLibre pitch/bearing behaviour (Table 2) is confirmed directly from official docs; three.js `OrbitControls`/`PointerLockControls`/`Raycaster` behaviour is confirmed from official docs plus community discussion (forum/GitHub), not from a live working demo built for this research pass.
