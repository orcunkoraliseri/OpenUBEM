## Part C — Synthesis (the migration map)

### (1) Verdict table restated as prose

Of the eight `idf_reader` assets in Table 1:

- **Reused verbatim (as-is, no code change needed):** none. Every asset needs at least a translation/adaptation layer before it can feed a web viewer — even `collect_geometry`, the strongest candidate, returns Python tuples that must become an indexed buffer.
- **Reused with adaptation:** `visualizer_adapter`'s low-level IDF-geometry-parsing primitives (already the shared foundation under everything else); `collect_geometry` itself (the single most valuable asset — see below); `idf_to_collada.py`'s triangulator and site→building→zone→category node hierarchy; `idf_to_sketchup.py`'s sub-surface repair and zone-multiplier full-floor expansion logic; the per-category colour values (as a seed palette, not as code); `neighbourhood_morphology.py`'s metrics-computation functions (as an attribute-value *source*, not a rendering asset).
- **Dead-ends for the web viewer:** `idf_reader/main.py`'s 4-view PNG batch driver; `idf_to_obj.py` in its entirety (OBJ format has no hierarchy/attribute support and browsers can't render it natively); `idf_to_sketchup.py`'s Ruby-script emitter (`_emit_ruby`, desktop-only); the matplotlib-specific painter's-order/z-fight workarounds inside both `render_idf_to_base64` and `render_geometry_to_base64` (a real depth-buffer renderer doesn't need them); `neighbourhood_morphology.py`'s own axonometric-rendering entry points (they are thin callers of already-counted assets, adding no new geometry logic).

### (2) Single most valuable reuse

**`collect_geometry` (`idf_to_sketchup.py:726-1069`).** It is the only asset in the audited code that already: (a) parses correctly for both EnergyPlus 8.x and 9+/22.x field layouts (via `_bsd_offsets`), (b) honours `GlobalGeometryRules` and per-zone origins, (c) separates opaque surfaces from sub-surfaces (the exact split `V04`'s two-LOD ladder needs), (d) groups everything by building and zone (a ready-made scene-graph skeleton), (e) already contains hard-won correctness fixes for real production data — the neighbour-aware window push-out clamp and the merged-neighbourhood sub-surface coordinate repair — that a fresh implementation would have to rediscover from scratch by hitting the same malformed-IDF edge cases, and (f) is proven general-purpose by being the literal shared dependency of all 3 existing exporters, not throwaway one-off code.

**Adaptation needed:** (i) add a stable per-surface ID to the `faces`/`subwin` tuples (currently only `building_key`+`zone_name`+`category` survive — the EnergyPlus surface name is available but discarded, Table 2 Q4); (ii) convert the flat-tuple-of-vertex-lists output into indexed vertex/index buffers (reuse `idf_to_collada._triangulate` for the n-gon→triangle step, which is already portable); (iii) extract `collect_geometry` out of `idf_to_sketchup.py` into a standalone shared module before building a 4th consumer on top of it (see Discrepancy #1 below) so a glTF/CityJSON emitter does not have to import from a file whose primary declared purpose is a SketchUp-Ruby exporter.

### (3) Confirmed gap list restated as the PLAN doc's new-build task list

1. **Geometry-interchange emitter** — new module translating `collect_geometry`'s (adapted) output into the `V03`-chosen web format, with indexed buffers + node hierarchy serialization. *(V03)*
2. **Stable feature-ID scheme** — extend `collect_geometry`'s tuples with a per-surface ID; design the join key to `eui_summary.json` / archetype / vintage attributes. *(V05)*
3. **Attribute-binding layer** — wires per-building/per-surface IDs to simulation outputs and to the metrics `neighbourhood_morphology.py` already computes (`dominant_typology`, `mean_height_m`, `wwr_*`, `FAR`, etc. — reusable as a *value source*). *(V05)*
4. **Interactive rendering stack** — full new browser renderer + camera/selection/navigation; nothing in the audited code is reusable here beyond the "4 canonical viewpoints" convention as a camera-preset idea. *(V06/V08)*
5. **Data-driven coloring/legend system** — new colormap/classification/legend layer; may seed its categorical defaults from the existing (but currently triplicated, Table 3) colour values after consolidating them into one source of truth. *(V09)*
6. **Geo-reference recovery** — a lat/lon→local-ENU transform recovering what both existing recentring steps actively discard; source data (`footprint_collector`) not verified in this audit — flagged as needing its own confirmation pass. *(V07)*
7. **Population data source** — genuinely new dependency; nothing in the 6 audited files computes or stores it. *(V05)*
8. **Colour-consolidation + colour-blind-safe audit** — before `V09` seeds its palette from the existing values, the 3 duplicated colour dicts (with at least one confirmed numeric drift — window alpha 0.70 vs 0.55) should be merged into one source of truth. *(V09, prerequisite housekeeping)*

### (4) Explicit flags against the `00_README_3dviz_prompt_set.md` shared-facts summary

1. **`collect_geometry` is described as if it were a standalone shared asset ("shared by the three CAD exporters"); it is not a separate module.** It is physically defined inside `idf_to_sketchup.py` (lines 726-1069) and imported *by name* into `idf_to_collada.py` (`idf_to_collada.py:34`) and `idf_to_obj.py` (`idf_to_obj.py:28`). This is accurate as far as "shared by" goes, but a reader of the README alone could reasonably assume it lives in its own geometry module — it does not, and any new web emitter that imports it today is importing from a module whose declared purpose (its own docstring) is "IDF -> SketchUp Ruby exporter." Recommend extracting it to a standalone module before a 4th consumer (a web emitter) is added — this is new-build housekeeping, not present today.
2. **`neighbourhood_morphology.py`'s primary purpose is understated / mischaracterized.** The README describes it purely as an axonometric renderer ("renders whole-neighbourhood axonometrics and 'full-floor' axonometrics… to PNG"). By the file's own docstring (line 1: *"IDF-only key-drivers report for the 35-neighbourhood fleet"*) and its default/only-documented public entry point `generate_all()` (line 922, the one referenced in the module docstring's "Public entry point" line), its main job is a **CSV + HTML metrics dashboard** (density/FAR, typology, height, orientation/WWR, HVAC summary, solar-access, net-zero-barrier-index), with a single axonometric PNG embedded as one card among many tables. The two functions that actually do neighbourhood/full-floor 3-D rendering (`generate_all_axonometrics`, `generate_all_fullfloor_axonometrics`) are separate, non-default entry points reached from a different item in `main.py`'s interactive menu (`main.py:141-146`). This matters for scoping: this file is a much more valuable reuse target for `V05`'s **attribute data** than for `V15`'s **geometry rendering**, which the README's phrasing does not make clear.
3. **Minor: window alpha value drift between the "one" colour convention the README states as a single fact.** The README states one canonical value set (wall/roof/floor/window/shading with specific hex+alpha) as if it were one convention; in the code it is at least three independently maintained definitions with a confirmed numeric mismatch (window alpha 0.70 vs 0.55, see Table 3 Q1). Not a functional bug in the current codebase (each renderer is internally consistent), but the README's framing of "the" colour convention obscures that there is no single source of truth to import from.

## Confidence and caveats

- **High confidence:** all claims about `visualizer_adapter.py`, `idf_to_collada.py`, `idf_to_obj.py`, `idf_to_sketchup.py`, and `main.py`'s `__4view__` branch — every behavioural claim above was traced to a specific function/line range in the actual file contents read in full during this audit.
- **Medium confidence:** claims about `neighbourhood_morphology.py`'s axonometric entry points (`generate_all_axonometrics`, `generate_all_fullfloor_axonometrics`) — the control flow was read and is accurate, but their dependencies (`BEM_utils.neighbourhood.build_neighbourhood_idf`, `Content.neighbourhoods.neighbourhood_registry`) were **not** opened in this audit (out of the 6-file scope); the merge step's internal geometry logic is therefore a **GAP**.
- **GAP — not verified in this audit (out of the required 6-file scope, flagged rather than assumed):**
