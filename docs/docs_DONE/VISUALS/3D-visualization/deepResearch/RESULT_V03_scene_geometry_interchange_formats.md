## Part C — Synthesis (the format decision)

### 1. Single recommended primary format: **CityJSON**

**Three decisive reasons:**

1. **Fidelity — zero forced transformation.** CityJSON is the only candidate format that stores IDF polygon geometry exactly as given (arbitrary vertex lists, no triangulation, no projection loss). OpenUBEM's hard constraint — *faithful to the model, no invented geometry or values* — is met unconditionally and provably (round-trip is vertex-level exact). glTF's required triangulation, while lossless for convex surfaces, is a transformation that introduces a testing burden and a non-trivial failure mode for non-convex surfaces. GeoJSON fails the faithful-to-model constraint completely and is a non-starter.

2. **Python emitter maturity and fit to the existing pipeline.** `cjio` is a TU Delft / OGC-community-maintained, MIT-licensed Python library with a stable API as of 2025. Emitting a CityJSON file requires only stdlib `json` (plus `cjio` for validation); no binary buffer construction, no accessor management, no spatial index. A new `idf_to_cityjson.py` module, reusing `collect_geometry` as the extraction layer, is the lowest-friction new emitter of any candidate — estimated 1 engineer-week to a tested module. The output is a single human-readable `.city.json` file per neighbourhood, matching OpenUBEM's outputs-discipline (one findable file in `openubem/outputs/`).

3. **Native dual-LOD expression in one file.** CityJSON's `"lod"` field on each geometry object (spec §4.1) allows both OpenUBEM LODs — surfaces-only neighbourhood mass (LOD 1) and surfaces+sub-surfaces building detail (LOD 2) — to coexist in one file per neighbourhood without duplicated authoring. Windows/doors are first-class `"Window"`/`"Door"` semantic surface types, requiring no extension.

**Caveat on direct web rendering:** CityJSON is not natively loaded by three.js or CesiumJS. It requires client-side triangulation (earcut) and a dedicated loader (`cityjson-threejs-loader` for three.js, as used by CityJSON Ninja). This is a known solved problem in the CityJSON ecosystem, not a blocker — but it means the browser-side rendering stack (V06) must include this loader. The triangulation for rendering happens in the browser, preserving the source polygon fidelity in the file.

### 2. Fallback / complementary format: **extruded GeoJSON** (for neighbourhood-scale LOD 0 context layer only)

A second, complementary format is warranted for *one specific purpose*: the lightweight, fast-loading neighbourhood-scale background view at maximum zoom-out, where the user has not yet selected a building and only needs building masses for orientation. For this purpose, extruded GeoJSON from the OSM footprints (already available in `footprint_collector`) can be emitted trivially and rendered natively in MapLibre GL JS or deck.gl without any IDF parsing.

**Explicit constraint:** this GeoJSON layer is a **LOD 0 footprint approximation only** — it must be clearly labelled in the viewer UI as such, and it must never be displayed where fidelity to the IDF model is claimed. The moment the user zooms to a building or requests an attribute heat-map on surfaces, the CityJSON geometry must be used. The GeoJSON layer is purely a navigational scaffold, not an energy model representation.

**Not recommended as a standalone format:** GeoJSON fails the faithful-to-model constraint for any surface-level representation and is a non-starter for per-surface attribute binding (V05).

---

### 3. What happens to `collect_geometry`

**Keep as-is; wrap with a new emitter.**

`collect_geometry` (the site→building→zone→per-category extraction function shared by `idf_to_collada.py`, `idf_to_obj.py`, and `idf_to_sketchup.py`) already performs the correct geometry extraction from IDF surfaces. Its output — a grouped dict of surface categories, each with 3D vertex lists — is **exactly what a CityJSON emitter needs**. The recommended path is:

```
collect_geometry(idf_path)
    → {zone: {category: [surfaces]}}
    → idf_to_cityjson.py (new module)
    → CityJSON dict construction (cjio or stdlib json)
    → neighbourhood.city.json
```

No changes to `collect_geometry` internals are required. The new `idf_to_cityjson.py` module is an **additional emitter** alongside the existing CAD exporters, not a replacement. This preserves all existing COLLADA/OBJ functionality (desktop-CAD targets) while adding the web-delivery path.

**One adaptation needed:** `collect_geometry` currently groups surfaces by category; for CityJSON the emitter needs to also carry per-surface metadata (surface name/ID, zone name, building ID) so each `WallSurface`/`Window` CityObject can be uniquely addressed by V05's attribute binding. This requires passing through the IDF surface identifiers (already present in the IDF object names), not a structural change to `collect_geometry`.

---

### 4. Downstream implications for V04 (LOD ladder) and V05 (attribute binding)

**V04 — LOD ladder:**
CityJSON's native `"lod"` field is the cleanest expression of OpenUBEM's two LODs:
- **LOD 1** (neighbourhood mass = surfaces only, no windows): emit wall + roof surfaces per building with `"lod": 1`.
- **LOD 2** (building detail = surfaces + sub-surfaces): emit all categories including `"Window"`/`"Door"` with `"lod": 2`.

Both LODs exist in the same `.city.json` file. The viewer (V06) loads the file once and switches displayed geometry by filtering on `lod`. The CityJSON loader (`cityjson-threejs-loader`) supports LOD filtering client-side. This means **LOD switching does not require reloading a file or a tiling service** — it is a client-side filter on an in-memory data structure. This is a major simplification over 3D Tiles' tile-streaming approach for OpenUBEM's neighbourhood scales (≤500 buildings), where the full geometry fits in browser memory.

**V05 — Attribute binding:**
CityJSON carries attributes natively in the `"attributes"` dict of each `CityObject` — no side-channel, no extension. Per-building attributes (archetype, EUI, carbon, `year_built`, `num_floors`) go directly into the building's `"attributes"`. Per-surface attributes (solar irradiance from EnergyPlus surface output, surface type, zone name) go into the semantic surface's properties. The binding path for V05 is:

```
eui_summary.json + IDF surface outputs
    → idf_to_cityjson.py (attribute injection step)
    → CityJSON "attributes" and semantic surface properties
    → cityjson-threejs-loader → three.js material/colour assignment
```

No `EXT_mesh_features`/`EXT_structural_metadata` extension complexity is required at the CityJSON stage. If the chosen rendering stack (V06) is glTF-only (e.g. CesiumJS with 3D Tiles), a conversion step (CityJSON → glTF + EXT_mesh_features) would be needed — this is a known conversion path supported by `py3dtiles` and `cjio`'s export modules, and it should be flagged to V06 as a dependency.

| Claim | Confidence | Caveat |
|---|---|---|
| glTF 2.0 requires triangulation | **High** — spec text §3.6.1 is unambiguous; confirmed by multiple independent sources. | None. |
| CityJSON preserves arbitrary polygons faithfully | **High** — spec §3 and §5 are clear; `cjio` programmatic API is documented and tested by TU Delft. | None. |
| `pygltflib` actively maintained 2025 | **High** — PyPI page confirms 2025 release. | Low-level API requires significant boilerplate for binary buffer construction; `trimesh` is a simpler alternative but with less control over feature IDs. |
| `cjio` actively maintained 2025 | **High** — cityjson.org cites active maintenance; PyPI updated 2025. | `cjio` is CLI-first; the Python API is less thoroughly documented than the CLI. Plain `json` stdlib may be preferred for the emitter. |
| File size estimates (glTF and 3D Tiles per-building/neighbourhood) | **Low — GAP.** No published end-to-end IDF→glTF→neighbourhood size benchmark exists. A manager should run a pilot conversion on a real OpenUBEM neighbourhood to measure. | |
| `py3dtiles` maturity for production use | **Medium.** `py3dtiles` is an active OSS project but less widely battle-tested than `pygltflib` or `cjio`. The last commit (mid-2024) suggests maintained but not high-velocity development. | If 3D Tiles is pursued, a pilot with `py3dtiles` should be run before committing. |
| CityJSON Ninja / `cityjson-threejs-loader` client-side triangulation performance | **Medium.** The earcut triangulator is a known, widely used algorithm. For hundreds of buildings with dozens of surfaces each, client-side triangulation at load time should be sub-second. | Torino heat-map repo geometry format | **Low certainty.** The GitHub repo `fereshtehsabeghi/Torino-3d-heat-mapping` was not directly accessible in web search results; the geometry format could not be confirmed first-hand.
