### Table 3 — LOD-switching mechanics fitness

Interaction: click-to-isolate fires an asset fetch and replaces the massing mesh with the windowed mesh. | **Good fit — recommended primary mechanic.** OpenUBEM's pipeline-as-Python-to-static-artifact pattern favours pre-built assets. The user's drill-down is a single discrete click → fetch/swap, not a streaming animation. The swap is instant if assets are pre-cached (≤100 kB per building glb is typical for IDF-scale geometry). ## Part C — Synthesis (the LOD ladder decision)

### 1. The Concrete LOD Ladder OpenUBEM Should Implement Now

OpenUBEM should implement a **two-level geometric LOD ladder** with a **conditionally-available third level** mapped to CityGML concepts:

1. **LOD-N (Neighbourhood LOD):**
   - **Geometry:** Closed solid massing mesh. Exterior wall and roof surfaces only; no windows/doors, no interior. Multi-polygon mesh from OSM footprint extruded to `num_floors × 3.5 m`.
   - **CityGML equivalent:** **LOD1** (block model, OGC 12-019 §10.3) / CityJSON `"lod": "1"`.
   - **Use case:** Neighbourhood-scale 3D camera navigation, thematic coloring by categorical function or sequential EUI at district scale.

2. **LOD-B (Building LOD):**
   - **Geometry:** Full architectural exterior. Walls + roof + floor + sub-surface window polygons + door polygons. Windows and doors rendered as distinct geometry layers (α 0.70 translucent blue). Shading surfaces optional second pass.
   - **CityGML equivalent:** **LOD3** (architectural shell with openings, OGC 12-019 §10.5) / CityJSON `"lod": "3"`.
   - **Use case:** Detailed building inspection, facade-level output visualization (per-surface solar radiation).

3. **LOD-Z (Zone LOD) — Conditionally Available:**
   - **Geometry:** Interior thermal zone partition slabs per floor (e.g. core + 4 perimeter slabs per floor). Derived by projecting zone boundaries onto floor levels.
   - **CityGML equivalent:** **LOD4** (interior spaces, OGC 12-019 §10.6) or **CityGML 3.0 interior LOD** (OGC 20-010 §9.3).
   - **Use case:** Diagnostic inspection of zone-level energy outputs, thermal load verification.

**Switching Mechanic:** **Discrete swap** (Table 3 recommendation). Pre-build two glb assets per building at pipeline run-time: `{building_id}_lod1.glb` (massing) and `{building_id}_lod3.glb` (windowed shell). LOD-Z geometry is embedded within `{building_id}_lod3.glb` as a hidden group activated by the UI toggle only if the resolution-mode gate passes.

---

### 2. The Resolution-Mode Gating Rule

This rule should be added directly to the visualizer design/PLAN documentation:

> **Rule V04-RMG-01 (Resolution-Mode Gate):**  
> Before rendering LOD-Z (zone-level) geometry or enabling per-zone attribute selection in the UI panel for a building, the viewer MUST read the `zoning_strategy` and `resolution_mode` metadata attributes bound to the building feature. The gate logic is:
>
> 1. If `zoning_strategy == "perimeter_core"`:
>    - **LOD-Z** is fully enabled. The viewer is authorized to render the interior core/perimeter zone partitions.
>    - The UI "Zone Breakdown" option is active.
> 2. If `zoning_strategy == "one_zone_per_floor"`:
>    - The viewer is authorized to render per-floor colour overlays (each floor slab as a single colour).
>    - An interior core/perimeter zone subdivision MUST NOT be rendered.
>    - The UI "Zone Breakdown" option is enabled but labelled as "Floor-level".
> 3. If `zoning_strategy == "single_zone"`:
>    - The viewer MUST refuse to render any interior subdivision or per-floor partitions.
>    - The UI "Zone Breakdown" option is disabled, showing a disclosure badge: *"Zone detail unavailable — building simulated as single zone"*.
>
> **Safeguard:** Procedural generation of synthetic zone boundaries (e.g., dividing a single-zone building into 5 visual quadrants in-viewer) is strictly prohibited. The viewer must only represent computed simulation divisions.

---

### 3. Zone-Level LOD Viability Assessment

The **LOD-Z (Zone LOD) is conditionally viable today** under the following parameters:
- **For the existing AUTO fleet:** Viable only for the **~5.8% (470/8,152)** of large multi-floor commercial buildings that AUTO simulated using the `perimeter_core` strategy. For the remaining ~94.2% (`single_zone` or `one_zone_per_floor`), LOD-Z is unavailable and must display the disclosure badge.
- **For new runs:** Fully viable for any building simulated under the user-selectable `fast_zone` or `zone` modes (as defined in `PLAN_resolution_mode_switch.md` §3), where the zoning strategy is forced to `perimeter_core` across all archetypes.
- **Verdict:** LOD-Z is a **functional feature today behind a metadata gate**. It is not a visualization gap, but its availability is governed directly by the dataset's simulation resolution.

---

### 4. Downstream Note for V08 (Drill-Down Mechanics)

The selection of a discrete swap switching mechanic imposes the following behaviors on `V08` (Navigation & Interaction):

- **Drill-down Click:** When a building is selected in the neighbourhood viewer:
  1. The viewer queries the building's metadata (already resident in memory).
  2. The viewer fetches and loads `{building_id}_lod3.glb` on demand (or retrieves it from local memory if pre-loaded in a single-file build).
  3. The viewer unloads or hides `{building_id}_lod1.glb` for the selected building.
  4. The UI panel updates its tabs: function, vintage, and EUI are activated. The "Zone Breakdown" tab is evaluated against **Rule V04-RMG-01** (enabled/disabled based on `zoning_strategy`).
- **De-selection / Auto-downgrade:** When the user de-selects the building or zooms out beyond the detail threshold:
  1. The viewer restores the visibility of `{building_id}_lod1.glb`.
  2. The viewer unloads `{building_id}_lod3.glb` from GPU memory to manage memory footprint at scale.
