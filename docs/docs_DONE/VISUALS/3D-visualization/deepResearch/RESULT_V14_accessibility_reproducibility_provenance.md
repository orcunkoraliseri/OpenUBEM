## Table 2 — Reproducibility

| Question | Answer + source |
|---|---|
| Given the same pipeline inputs and the same code version, does the recommended viewer build produce a byte-identical (or otherwise verifiably identical) artifact? | **Yes, in principle, but this is a NEW guarantee the viewer-export step must add — OpenUBEM's existing determinism rule does not automatically extend to it.** The pipeline already guarantees determinism upstream: all stochastic imputation draws flow through `np.random.default_rng(config.RANDOM_SEED)` (default seed 42) so re-running the same code+inputs reproduces byte-identical enriched attributes and IDFs (`PLAN_input_imputation_implementation.md:140-141`, Rule 8). EnergyPlus itself is deterministic given identical IDF+EPW+version. **However**, the interchange-format *export* (geometry → glTF/CityJSON/whatever `V03` picks) is a new code path this set is adding, and export order (e.g. dict/set iteration when building feature ID tables, floating-point serialization precision, timestamp embedding) can silently break byte-identity even when the physics inputs are unchanged. **Requirement: the export step must sort/order deterministically (fixed building/zone iteration order, e.g. by `osm_id`) and must NOT embed a wall-clock build timestamp inside the content-hashed portion of the artifact** (a separate, un-hashed metadata field can carry the timestamp — see row 2). This is GAP for the *specific* serialization library `V03`/`V06` chooses — the manager must re-verify byte-identity empirically once that stack is picked, this report can only state the requirement. |
| What should be embedded in the artifact to make its provenance self-evident (pipeline run ID/commit hash/timestamp, resolution-mode summary)? | A **metadata block** embedded in the exported scene (glTF `asset.extras`, CityJSON `metadata`, or an adjacent sidecar JSON if the format has no native slot — GAP: format-specific mechanism deferred to `V03`/`V05`) carrying, at minimum: (1) **git commit hash** of the OpenUBEM checkout that produced the run (standard software-reproducibility practice — RESULT_16 Table 4 row 4 already mandates this be logged in "project run metadata" alongside EPW filename and seed: `RESULT_16...md:44-47`); (2) **pipeline run ID / build timestamp** (kept in the un-hashed metadata region per row 1); (3) **`RANDOM_SEED`** used (`config.RANDOM_SEED`, default 42); (4) **per-neighbourhood `resolution_mode` summary** — a count of buildings by mode (since a single export can mix `auto` with a forced pilot mode); (5) a **link/reference to the source `manifest.parquet`/`05_results.*` files** so a user can trace any displayed value back to the exact row that produced it (this is the mechanism Table 4's "value round-trip" validation exercises). This composition follows the **FAIR Reusable principle** — metadata must be "sufficiently annotated so machine and human users can determine fit-for-purpose" (Wilkinson et al. 2016, *Scientific Data* 3:160018) — applied to a generated visualization artifact rather than raw research data. |
| What is the versioning story if the coloring spec (`V09`) or LOD ladder (`V04`) changes between pipeline runs — does an old exported viewer silently become inconsistent with a new one? | **It can, and the mitigation is a spec-version field, not a promise of eternal compatibility.** Embed a `viewer_spec_version` (or two: `coloring_spec_version`, `lod_spec_version`) string in the same metadata block as row 2, incremented whenever `V09`'s colormap/classification rules or `V04`'s LOD ladder change. An exported artifact is then **self-describing but not self-updating** — opening an old export always reproduces exactly what it showed the day it was built (this is *correct*, not a bug: it is what "reproducible" means), but the viewer's own UI/legend code should read `viewer_spec_version` and, if it does not match the current build's expected version, show a small non-blocking banner ("this export uses an older colour spec — legend may not match current convention") rather than silently re-interpreting old data under new rules (which would be a **faithful-to-model violation** — the two hard constraints explicitly forbid changing what is displayed without the user knowing). GAP: the exact `V09` colormap version-bump policy (semver? date-stamp?) is `V09`'s decision, not re-derived here. |

## Part C — Synthesis (the provenance & trust spec)

**(1) Concrete provenance-surfacing design.** Two badges plus one border treatment, all bound to fields that already exist in OpenUBEM's own schema — nothing here requires a new upstream computation:

- **Resolution-mode border treatment** (neighbourhood LOD): footprint outline weight/style keyed to the literal `resolution_mode` string (`building`/`floor`/`fast_zone`/`auto`; `zone` reserved for when it ships) — thin solid for `building`, medium for `floor`, heavy for `fast_zone`/`zone` — **plus** a text badge on hover/select that states the mode in words, satisfying the non-colour-only rule (Table 3 row 4) without pre-empting `V09`'s colour system. Source field: `resolution_mode` in `manifest.parquet`/`05_results.*` (RESULT_16 Table 4).
- **Trust/confidence badge** (both LODs, on selection): a single merged 3-state glyph (not colour-only — shape-differentiated, e.g. solid/half/hollow) driven by the **lower** of `mean_imputation_confidence` (input-provenance) and `archetype_confidence` (classification-provenance), since either one being LOW should visually dominate — a building cannot be "trustworthy overall" if its archetype guess is `LOW` even when its numeric inputs are fully observed. Clicking/hovering opens a detail pane listing the raw `data_quality_flag` tokens, `archetype_source`, and `imputed_fields_count` verbatim (never re-worded or summarized away — auditability requires the literal token, per the imputation arc's "queryable marker" rule, `PLAN_input_imputation_implementation.md:128-130`).
- **No-data / failed-generation treatment**: `generation_status != "success"` buildings render in a desaturated hatched material (an *extrinsic* uncertainty encoding per Table 3's uncertainty-visualization citation) rather than being dropped from the scene, with the literal status string on hover.
- **Schema home for all three**: these ride in the same feature-attribute table `V05` designs for binding EUI/carbon/population to geometry (glTF `EXT_structural_metadata` / 3D-Tiles batch table / GeoJSON properties, per whichever format `V03`/`V05` land on) — provenance fields are just three more attribute columns (`resolution_mode`, `mean_imputation_confidence` + `archetype_confidence`, `generation_status`) in that same table, not a parallel side-channel. **This is a hard requirement, not a preference**: if provenance rides a different binding mechanism than the value attributes, the two can drift out of sync silently, which is exactly the failure mode this prompt exists to prevent.

**(2) Reproducibility rule.** Every exported artifact embeds a metadata block (Table 2 row 2) carrying: git commit hash, `RANDOM_SEED`, pipeline run ID + build timestamp (kept in an un-hashed region so it doesn't break content-addressability), a per-mode building-count summary, and `viewer_spec_version`/`lod_spec_version` strings. The export step itself must be deterministic in iteration order (fixed sort key, e.g. `osm_id`) so that re-running the *same* pipeline state produces a *verifiably identical* artifact — verifiable via a content hash of the geometry+attribute payload (excluding the un-hashed timestamp field). This is FAIR's Reusable principle (Wilkinson et al. 2016) applied to a generated visualization rather than raw data, and is additive to — not a replacement for — OpenUBEM's existing `RANDOM_SEED`-based upstream determinism.

**(3) Accessibility minimum bar for MVP.** **Must-have:** WCAG 2.1 SC 1.4.3 (4.5:1 text contrast), SC 1.4.11 (3:1 non-text/graphical-object contrast — directly binds the provenance badges), SC 2.1.1 (all 2-D UI chrome — legend, filters, attribute selector, detail pane — fully keyboard-operable; Tab-cycle building selection as the 3-D-canvas keyboard minimum), and the non-colour-only rule (every colour-encoded value has a redundant text/shape/tooltip encoding — this is the one that makes the provenance badges *and* `V09`'s heat-maps trustworthy for CVD users). **Deferrable to post-MVP:** WCAG AAA-level contrast (7:1), full free-fly keyboard camera control beyond selection-cycling (SC 2.1.1's letter exempts path-dependent navigation), and screen-reader/ARIA support for the 3-D canvas itself (the 2-D chrome around it should still be screen-reader-navigable, but narrating a live 3-D scene is a known hard problem across the whole field, not something this MVP should block on — **GAP**, no peer UBEM tool found in this pass to cite as doing this).

**(4) Validation procedure the manager should run before accepting any viewer build as faithful** (concrete enough to become PLAN checkpoints):
1. **CP-Geometry**: on a stratified sample (≥1 building per archetype × per resolution-mode combination present in the export), automated vertex round-trip against the source IDF, tolerance ≤1cm (Table 4 row 1). Fail = block ship.
2. **CP-Value**: automated diff of every displayed numeric attribute (EUI/carbon/end-use) against `05_results.csv`, exact or float-tolerance match, for 100% of exported buildings (cheap to automate fully, no sampling needed — Table 4 row 2). Fail = block ship.
3. **CP-Provenance**: automated diff of every badge-driving field (`resolution_mode`, `mean_imputation_confidence`, `archetype_confidence`, `generation_status`, `data_quality_flag`) against the enriched-semantics/manifest source tables, 100% coverage, plus the negative-case check (a zero-imputation building shows "fully observed") — Table 4 row 3. Fail = block ship.
4. **CP-LOD**: automated sub-surface/zone count check per `resolution_mode` (Table 4 row 4) + a manual visual spot-check of one building per mode by the manager. Fail = block ship.
5. **CP-Accessibility**: automated contrast-ratio check (SC 1.4.3/1.4.11) on the legend/badge/tooltip palette actually shipped by `V09`, manual keyboard-only walkthrough of selection + filter + legend (SC 2.1.1), manual CVD-simulation pass (Coblis/Chromatic-Vision-Simulator-class tooling, **GAP — specific tool not independently verified this pass**) over the final colour system. Fail on contrast/keyboard = block ship; fail on CVD = escalate to `V09` for palette revision, not a `V14` fix.
6. **CP-Reproducibility**: re-run the same pipeline commit+seed twice, diff the two exports' content hash (excluding the un-hashed timestamp field) — must match. Fail = block ship.

These six checkpoints are the enforcement mechanism the faithful-to-model hard constraint needs; none of them exist today because no interactive viewer exists today (00_README: "there is no interactive, web, or output-driven viewer").

## Confidence and caveats

- **Least-evidenced pattern: provenance/confidence surfacing for imputed-vs-observed inputs in a 3-D UBEM viewer.** The peer-tool search in this pass (CEA, UMI, ubem.io) turned up **no evidence that any shipped UBEM visualization tool exposes per-building data-provenance or imputation-confidence as a first-class visual affordance** — the closest finding was a validated-UBEM confidence-*band* on aggregate heating/cooling demand (±15%/±12.5%), which is a statistical accuracy statement about the model as a whole, not a per-building "this value was imputed, not observed" flag rendered in the viewer. This is consistent with the broader UBEM-tools literature's focus on aggregate calibration/validation metrics rather than per-object data lineage. **This means the Table-1 badge design in this report is closer to novel UX design than a documented industry convention** — it is grounded in general uncertainty-visualization literature (MacEachren, Pang, Padilla/Kay/Hullman) and OpenUBEM's own already-computed fields, not in an existing UBEM-viewer precedent. Flag this explicitly to the manager: this is where the plan should budget extra design-review time, since there is no reference implementation to copy.
- **GAP — exact serialization-format mechanism for embedding provenance metadata** (glTF `asset.extras` vs `EXT_structural_metadata` vs a sidecar file) is deliberately deferred to `V03`/`V05` per this prompt's scope guard; this report states the *requirement* (self-evident, queryable, versioned metadata) not the *mechanism*.
- **GAP — WCAG SC 1.4.1 (Use of Color)** was not independently fetched this pass (implied/cited by inference from the CVD and non-colour-only rows); if this becomes a binding PLAN checkpoint, re-verify the exact clause text before citing it as a hard requirement.
